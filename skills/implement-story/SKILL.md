You have been given a **story** bead id: the part of one feature that lands in one repo, parent of that repo's tickets. The issue tracker rules are in `${CLAUDE_PLUGIN_ROOT}/docs/agents/issue-tracker.md`.

The goal is the story implemented on a single **integration branch** in its owner repo, every `ready-for-agent` ticket closed, reviewed once, and delivered as a PR (or, with no forge, the branch).

The tickets are not a list of steps. They are a **task graph** with blocking relationships between them, so there is always a **frontier** of tickets ready to be grabbed.

## Shared rules

The session running this skill is the **story orchestrator** and follows `${CLAUDE_PLUGIN_ROOT}/docs/agents/orchestration.md`: Orchestrator role, Scratch space, Complexity tier and Frontier. Read it before step 1. "The tier's model", "the frontier", "human stop" and "stall" below mean those sections. Communication to and from subagents goes through context pointers (story bead, ticket beads, notes, commits), never copies.

## Owner repo

`<owner>` is the absolute path of the story's owner repo: the session's repo (`git rev-parse --show-toplevel`) when `/dev:implement-story` is typed there, else the path in the brief that spawned you. The procedure below is the same either way, with the repo as its parameter:

- every `bd` command, by every agent, is `bd -C <owner> …`, with one exception: the inbox capture of a deferred finding (step 7, and the ticket runner brief's step 3) is plain `bd`, which reaches `<home>`'s database from where every agent runs, as the tracker doc's "capture a retro item" says;
- `git` follows where the agent works. You, a ticket runner and a merger run `git -C <owner> …` on the owner checkout (a merger also `git -C <worktree path>` on the implementer's branch). An implementer on the hand-rolled route runs `git -C <worktree path> …`. A harness-isolated implementer runs plain `git` in its own worktree, which is its working directory; `git -C <owner>` would put its commits straight onto the integration branch;
- every file path is absolute, under `<owner>` or the agent's worktree; the shell stays where it started and never `cd`s;
- paths are spelled out literally, one command per Bash call, as the rules doc's Scratch space says (Literal paths);
- every forge command names the repo (step 3);
- every brief to a subagent carries `<owner>`, the worktree path when it has one, and the `git` rule for that agent;
- every brief to an agent that works in a worktree (implementer, fix-up implementer, merger) starts with the **TMPDIR line** of the rules doc's TMPDIR rule (Scratch space), `mkdir -p <worktree>/.tmp && export TMPDIR=<worktree>/.tmp` with the worktree path spelled out (on the harness route the implementer fills in the path `pwd` prints), and its two riders: `export TMPDIR=<worktree>/.tmp;` repeated at the head of every Bash call that runs `mktemp`, a heredoc or a script, and `mktemp -d <worktree>/.tmp/<name>.XXXXXX` in place of a bare `mktemp -d`, which macOS runs under `/var/folders` whatever `TMPDIR` says;
- every brief that points at a doc under `<plugin root>/docs/agents/` (orchestration.md, issue-tracker.md, coding-standards.md, any other) spells its absolute path literally, `<plugin root>/docs/agents/<doc>.md` with `<plugin root>` replaced by the path this session resolved (the rules doc's Plugin root rule), never an environment variable and never a `~/` path: a subagent's Bash has no such variable. A pointer such as "the rules doc's Idle rule" in a brief names that doc by the same absolute path, which the runner brief below states once.

`<owner>` outside `~/src`, when it is not the session's repo, makes `bd` and `git` writes fail with `Operation not permitted`: the tracker doc's "bd writes outside the session's repo" says what to do. The session mode, `<home>` and `<workspace>` are as **the one test** in the tracker doc's opening defines them: `<home>` is the session's repo, the workspace for a spawned story orchestrator and the owner repo for a typed one, and plain `bd` reaches its database. Typed in an owner repo, the session is a repo session with no workspace, and what needs another database degrades: the sibling line, the sibling refresh with step 8's sibling re-read (step 3), and the `waiting:` line (step 9) are skipped, and a text blocker in another repo cannot be read, so it counts as open (the Frontier section's unreadable-blocker rule). A story cut in such a repo session runs right there. Only a story whose text blocker is in another repo is run from the workspace session: its wait message says to run `/dev:implement-spec <KEY>-<n>` (or `/dev:implement-spec <epic-id>` when the epic has no external ref) from the workspace root (`/dev:implement-story <story-id>` typed there would take `<owner>` for the workspace and not find the story).

`<KEY>-<n>` is the story's `external_ref`. A story without one has no key: its commits carry `Bead:` alone (no `Refs:`), and the sibling line (`<repo> <story-id> <url>`) and the Jira context below are skipped; its branch is `feat/<story-id>`, as every story's is (step 3).

`<ticket-slug>` is the ticket id; `<epic-id>` is the epic bead id on the story's `## Parent` line. **Worktrees**: harness isolation (`isolation: "worktree"`) makes worktrees only in the session's repo, so a subagent working in `<owner>` takes it only when `<owner>` is the session's repo. Otherwise its worktree is hand-rolled inside `<owner>`, as the rules doc's fallback: `git -C <owner> worktree add <owner>/.worktrees/<ticket-slug> -b ticket/<ticket-slug> <integration branch>` (reused if it exists; when only the branch survives, re-add it as the rules doc's fallback says), and the brief gives its absolute path.

## Steps

1. **Read the story and its tickets.** `bd -C <owner> show <story-id> --json` (an array; `.[0]`). Refuse with one line and create nothing when:
   - the bead is an epic whose direct children (`bd -C <owner> children <id> --json`) include a non-story bead: `<id> refused: flat epic (tickets directly under the epic bead); the story skills do not handle it — the small-bug path does: /mattpocock-skills:implement <ticket-id> per ticket, then bd close <epic-id>`;
   - otherwise the bead is not of `issue_type` `story`: `<id> is of type <type>, not a story; /dev:implement-story takes a story bead id.`

   The tickets are `bd -C <owner> children <story-id> --json`. The story's **tier** is the max `complexity:` label among them. The story's notes (`.[0].notes`) are what earlier runs left behind, one line each: `branch:` (step 3), `review:` (step 7) and `pr:` (step 8); read them once here, the last line of a kind winning. A story is **finished** when every child is `closed` or carries `ready-for-human`, `needs-triage` or `wontfix` (the rules doc's Frontier, Deferrals) and its notes carry a `pr:` line: touch nothing, and go straight to the final report (step 9) with the `pr:` and `branch:` lines read from the notes.

   **Merge guard.** The guard covers a delivered story with an open `ready-for-agent` ticket: one whose notes carry a `pr:` line, a URL or step 8's `<branch> <tip SHA>` form, while a child that is not closed (open, in_progress or blocked) is labelled `ready-for-agent` (a ticket added after the first delivery, ADR 0011's add mode). A URL goes to one forge query; the branch form or no forge is decided locally first, then asked (below). The query decides, with the forge decided as step 3 says (its remote pre-check and proof run here first), run with the sandbox disabled, as `/dev:close-story` step 4 does: `gh pr view <url> --json state`, or `tea api --repo <owner> repos/{owner}/{repo}/pulls/<n>` and its `"merged"` and `state` fields (a Forgejo `state` reads `closed` for merged and unmerged alike). MERGED: refuse with `<story-id> refused: PR <url> already merged; the new ticket belongs in a new story: run /dev:spec-to-stories <KEY>-<n> in add mode (or /dev:spec-to-stories <epic-id> when the epic has no external ref); then close <ticket-id> (moved to the new story)` and create nothing; the line names each open `ready-for-agent` ticket as `<ticket-id>`, which stays open under the merged story until add mode has carried its work into a new story, so close it there then (`/dev:close-story` cannot). CLOSED unmerged: refuse with `<story-id> refused: PR <url> is closed unmerged` and create nothing. OPEN: continue on the `branch:` note's branch, the re-delivery path of steps 3 and 8. When the forge cannot tell (no forge, or a branch-form `pr:` note), decide the branch form locally first: `git -C <owner> fetch origin` (skipped with no `origin`), then `git -C <owner> merge-base --is-ancestor <tip SHA> origin/<default branch>` (exit 0: as MERGED; exit 1: as OPEN; a failed fetch of an existing origin or any other exit: it cannot decide (ask)); find `<default branch>` as step 3 says; with no `origin`, compare against the local `<default branch>`. Ask the user only when that cannot decide, whether the PR, or for the branch form the branch, has merged into the default branch, and wait for the answer. In a run spawned by `/dev:implement-spec`, which has no user (the rules doc's Delivery), end instead with `failed: <story-id> merge state unknown (<pr: value>): say whether it merged, then re-run` and create nothing. A failing forge command is an error, reported as `<story-id> refused: forge check failed: <error>`, never as "no forge".

   Read the story's `## Blocked by` lines and check each as the Frontier section says (a blocker naming a story reads like any bead: open until `/dev:close-story` closes it). While any is open, no ticket can start: report `<story-id> waits on <repo> <bead-id> <title>` for each (a story blocker adds `merge its PR and run /dev:close-story <blocker-id>`; in a repo session, a blocker in another repo cannot be read: show its line as written in place of the title, and add `run /dev:implement-spec <KEY>-<n> from the workspace root`, or `/dev:implement-spec <epic-id>` when the epic has no external ref), and stop before any branch or commit exists.

2. (optional) Use an **exploration subagent** for any exploration the tickets need. Its brief names the story bead and `<owner>`; it reads the story's design field first (`.[0].design` of its own `bd -C <owner> show <story-id> --json`), the story cut's orientation for this repo, and writes its own notes into `<owner>/.spec-notes/<epic-id>/`, the directory this skill alone owns (the rules doc's Scratch space); every later brief points there by that absolute path.

3. **Integration branch.** A `branch:` line in the story's notes means an earlier run made it: `git -C <owner> switch <name>` if the owner checkout moved off it, and keep any draft PR it opened. Otherwise find the default branch (`git -C <owner> symbolic-ref --short refs/remotes/origin/HEAD` minus `origin/`; with no `origin/HEAD`, whichever of `main` and `master` exists), then `git -C <owner> switch -c feat/<story-id> <default branch>` (the branch is named `feat/<story-id>`, keyed or not: the key stays on commits, the PR body and the bead) and `bd -C <owner> note <story-id> "branch: <name>"`. The owner checkout stays on the integration branch until the run ends; mergers merge into it there.

   Apply the rules doc's Gitignore rule on the integration branch: append each missing entry with one shell command (`printf '%s\n' /.claude/worktrees/ >> <owner>/.gitignore`, and so on). Then, when `git -C <owner> status --porcelain -- .gitignore` prints anything, the file is dirty: with an entry appended here, or with one an earlier run appended and was cut off before committing. When every added line in `git -C <owner> diff -- .gitignore` (every line of the file, when it is untracked) is one of the rule's four entries and no line is removed, commit it: `git -C <owner> add <owner>/.gitignore` and `git -C <owner> commit -m "chore: ignore agent scratch space" --trailer "Bead: <story-id>" --trailer "Refs: <KEY>-<n>"` (no `Refs:` with no key). Any other line is an edit of the user's, which the rules doc's Commits rule would stop at the first merge: end the run now with `failed: <owner>/.gitignore has uncommitted edits; commit or stash them and re-run`, and a switch above that git refused over that file ends the run the same way. This is the repo plumbing the Orchestrator role allows; it is never done with `Edit` or `Write`.

   Decide **once** which forge fronts the repo (already decided in step 1 when the merge guard ran). Pre-check `git -C <owner> remote get-url origin`: `github.com` → `gh`; a Forgejo/Gitea host → `tea`; a plain `ssh://host/path.git`, a bare path, or no remote → none. Both CLIs otherwise act on the working directory's repo, so every forge command names its repo: `gh … --repo <forge-slug>`, with `<forge-slug>` the `owner/name` part of that repo's `origin` URL; `tea … --repo <path>`, which takes the repo's absolute path and finds the remote and login from it. For the owner repo that is `<forge-slug>` of `<owner>` and `--repo <owner>`. Prove the forge with `gh repo view <forge-slug>` or `tea pr list --repo <owner> --limit 1`. Forge CLIs keep their tokens outside the sandbox, so inside it they fail with `unable to get or create config file`, which is not a missing login: run each forge command with the sandbox disabled. A failure outside the sandbox is real (`no available login` → the user runs `gh auth login` or `tea login add`): stop and report it.

   Resolve the owner repo's **lint command** once, here beside the forge, and keep it for the run: `make lint` when `<owner>`'s Makefile has a `lint` target (`grep -q '^lint:' <owner>/Makefile`), else the command `<owner>`'s `CLAUDE.md` names, else none. The ticket runner brief's header carries it as `<lint>`, and a runner spells it out in every implementer, fix-up implementer and merger brief it sends (and step 7 does the same for the story review's fix-up and merger), so no agent guesses it. `make lint` runs as `make -C <dir> lint` in the checkout or worktree it checks, and a command `CLAUDE.md` names runs in that same checkout or worktree, spelled with absolute paths and no `cd`. It is a repo fact, not a story field: the story body and the story cut carry none.

   With a forge, open a **draft PR** after the first batch (step 4) that contains a `closed` report (a branch with no commits ahead of the default branch cannot open one). Mergers' merges are local, and naming `--head` stops `gh` pushing for you, so first run step 8's **stray-commit check** (a hit ends the run there, as step 8 says), then **push** the integration branch, `git -C <owner> push -u origin <branch>`, on the typed command's authority (the rules doc's Delivery); a refused push leaves the draft unopened for now, the frontier is worked on (the merges are local), and step 8 pushes again. With the branch pushed, `gh pr create --draft --repo <forge-slug> --head <branch> --base <default branch> --title "<story title>" --body-file -`, or `tea pr create --repo <owner> --head <branch> --base <default branch> --title "WIP: <story title>" --description "<body>"` (Forgejo treats the `WIP:` prefix as draft). Its body names the story, the Jira key, and one **sibling line** `Part of <KEY>-<n>:` listing the sibling stories: every other `story` bead carrying `<KEY>-<n>` in the manifest's repos (the "Stories" gather in the tracker doc, whose `--json` output carries each sibling's notes). Each sibling appears as `<repo> <story-id> <url>`, the url taken from its `pr:` note; with no `pr:` note, from its draft PR looked up by its `branch:` note in `<workspace>/<repo>`. A sibling's forge is decided from its own `git -C <workspace>/<repo> remote get-url origin`, as above for the owner: `gh pr list --repo <its forge-slug> --head <branch> --json url -q '.[0].url'`, or `tea pr list --repo <workspace>/<repo> --state open --fields head,url --output json` filtered on `head`. Only when neither exists (a sibling with no forge, or no draft yet), `<repo> <story-id> <branch>`. Then run the **sibling refresh**: in each sibling's open PR, regenerate the whole `Part of <KEY>-<n>:` block from the Stories gather's current notes on every run, listing every story of the feature but that sibling, this story's PR included, and never patch single lines. Both edit commands replace the whole body, so read it first and write all of it back on stdin, with the sibling's own CLI and repo: `gh pr view <n> --repo <its forge-slug> --json body -q .body` then `gh pr edit <n> --repo <its forge-slug> --body-file -`, or `tea api --repo <workspace>/<repo> repos/{owner}/{repo}/pulls/<n> | jq -r .body` then `tea pr edit <n> --repo <workspace>/<repo> --description-file -`. A sibling with no forge or no open PR is skipped. With no forge the integration branch *is* the deliverable; a request for a PR is answered with the branch name.

4. **Work the frontier.** A ticket of the story that is `in_progress` while no runner of this run holds it was claimed by a cut-off run (the rules doc's Cut-off agents): `bd -C <owner> unclaim <id>` each first. An unclaim bd refuses because another actor holds the claim is never forced: the ticket is off this run's frontier, with `failed: <id> claimed by <actor>` in step 9's report. Then `bd -C <owner> ready --parent <story-id> -n 0 --json`, keeping only the tickets labelled `ready-for-agent` (the rules doc's Frontier: `bd ready` lists a `ready-for-human` or `needs-triage` child all the same) and minus the tickets that failed twice in this run (step 5; a twice-failed ticket is open and unclaimed, so `bd ready` lists it, and only this run's count keeps it off). Step 1 already cleared the story's text blockers. Spawn one **ticket runner** per frontier ticket with `subagent_type: "general-purpose"` (the rules doc's Subagent type) at `model: opus`, the whole current frontier as one parallel batch in one message, then end your turn: each runner's report line arrives as the Agent tool's completion notification and resumes you (the rules doc's Waiting: an Agent call returns at once, and you never poll). Fill the brief below. Spawn nothing else per ticket: the runner owns the ticket's implementer, reviewer and merger.

   **Resumed.** A `resume:` line from the driver means the batch in flight was cut off and its agents stopped: re-read the story's notes as step 1 does (`branch:`, `review:`, `pr:`), confirm the owner checkout is on the integration branch (step 3), and go to step 6, where the unclaim above returns the cut-off tickets to the frontier. A typed run that was cut off is re-typed by the user and takes the same path from step 1.

   When a text blocker is a publish ticket (titled `publish <crate> <version>`), the brief also carries the published version: the version in that blocker's `close_reason` (written `published <version>`), which wins over the version in any title. No version in the reason → ask the user for it and wait.

5. **Act on every report of the batch**, each as its notification resumes you. Each runner reports one line:
   - `<id> closed`: nothing more for that ticket. The first batch with one opens the draft PR (step 3).
   - `<id> needs split: <cut>`: create the proposed beads as children of the story, each `bd -C <owner> create --parent <story-id> --labels complexity:<tier>,ready-for-agent --deps blocked-by:<new-id>,... "<title>" --body-file -` with the edges and the tier the cut proposes for that bead (else the original's tier); move every bead the original blocked onto the new ones (`bd -C <owner> dep add <dependent> <new-id>`, so a publish ticket still waits on all of the story's work); close the original with `bd -C <owner> close <id> --reason "split into <ids>"`.
   - `<id> failed: <reason>`: the runner ended without closing its ticket, and its claim outlives it (the rules doc's Frontier, Unclaim), so first `bd -C <owner> unclaim <id>` (a refusal follows step 4's rule). A first failure gives it one fresh runner in the next batch with the reason added to its brief. A second failure takes the ticket off the frontier for this run: `bd -C <owner> note <id> "failed twice: <reason>; resume: <command>"` with step 9's resume command, so the ticket stands open and unassigned, `bd -C <owner> ready --parent <story-id>` lists it, and a resumed run finds the pointer; it is a `failed:` line in step 9's report. An API error in place of a report line is a cut-off, not a failure: the ticket rejoins the frontier at step 6 through step 4's unclaim, its failure count unchanged.

6. **Re-evaluate the frontier** once every report of the batch has arrived and been handled, and spawn the next batch from it (step 4). Repeat until a batch would be empty. Then:
   - every child is `closed` or carries `ready-for-human`, `needs-triage` or `wontfix`, what step 1 counts as finished short of the `pr:` note → steps 7 and 8. A child carrying one of those labels is not waited for (the rules doc's Deferrals);
   - otherwise skip steps 7 and 8 and go to step 9. The run is a **human stop** if a `ready-for-human` ticket of the story is open and a **stall** otherwise, as the rules doc says; either way the report names each other child left open.

7. **Story review.** First the **review marker**: compare the story's `review:` note with the integration branch tip, `git -C <owner> rev-parse <branch>`. The same SHA means an earlier run reviewed this tip and merged its fix-up: skip the gate and the review and go to the Evidence run below. No note, or a tip that has moved since, means the review is due, and the **check gate** on the integration branch tip runs first (the rules doc's Check gate; how a check runs is below): a red goes, as the failing command and its log path, to the fix-up implementer below, then its merger, for one round, and the gate runs again on the new tip; a second red skips the review and step 8 and goes to step 9, classified as step 6 says, with a `failed: <check> <command>` line in the report. With the gate green, call the Skill tool with `mattpocock-skills:code-review` on the integration branch since the default branch in `<owner>`, with its two sub-agents run at the review model of the story's tier. The skill reviews the working directory's repo, so the invocation names `<owner>` and spells out what its sub-agents receive: the diff `git -C <owner> diff <default branch>...<branch>` and the commit list `git -C <owner> log <default branch>..<branch> --oneline`; standards sources searched in `<owner>` (its `CODING_STANDARDS.md` or `CONTRIBUTING.md`, `GLOSSARY.md` and `docs/adr/` where they exist) plus `<plugin root>/docs/agents/coding-standards.md` spelled as the path this session resolved (the bullet above), which the skill never finds on its own; and the spec named explicitly: the story bead and its tickets, with the Jira epic `<KEY>-<n>` for the feature context; and the shape of each sub-agent's report, as the rules doc's Review verdict says: every finding tagged **blocking** or **minor**, the last line `verdict: clean` or `verdict: blocking (<n>)`. Its sub-agents report findings only and create no bead. The story tier has one round and never fails on a verdict: blocking and minor findings alike go to the fix-up implementer below, and the story proceeds to delivery after it, so a two-axis review that is minor-only on both axes proceeds as any other does; the tags serve the reader of the report and the deferral decision. Findings go, as a pointer, to one **fix-up implementer** at the tier's implementation model in its own worktree (Owner repo's Worktrees rule, slug `fixup-<story-id>`; its brief starts with the TMPDIR line for that worktree and names the ten-minute limit on lint and test runs, `timeout: 600000` on every lint and test run, as the ticket runner brief's step 2 says; its commits carry `Bead: <story-id>` and `Refs: <KEY>-<n>`, no `Refs:` with no key), followed by a merger at the same model briefed as the ticket runner's step 4; both briefs carry `<owner>` and the lint command step 3 resolved, spelled out (or none). You relay, you never fix. A finding the review defers (out of the story's scope, a follow-up, a note with nothing to implement) goes to no implementer and to no child of the story: capture it in the inbox as the tracker doc's "capture a retro item" says (plain `bd` in `<home>`, that section's command, labels and target label, `<KEY>-<n>` as the external ref when there is a key, the finding as the body's Moment), so no later run's frontier sees it (the rules doc's Frontier, Deferrals). The fix-up implementer's brief says the same: what it cannot fix within the story comes back in its report, never as a bead. Once the fix-up is merged (or the review found nothing to fix), write the marker: `bd -C <owner> note <story-id> "review: <tip SHA>"` with the tip re-read after the merge (`git -C <owner> rev-parse <branch>`).

   **Running the checks.** The checks are the lint command step 3 resolved, then the story's test seams (its body names them), cheapest first, the first red stopping the run. Each runs read-only on the integration branch tip in `<owner>`, through the tool's own directory flag or absolute paths (`make -C <owner> lint`, `cargo test --manifest-path <owner>/Cargo.toml`, `make -C <owner> …`), one foreground Bash call per check with `timeout: 600000` (the rules doc's Idle rule), both streams going to a log under the owner checkout's `.tmp/` and the exit code echoed: `mkdir -p <owner>/.tmp/checks-<story-id>` once, then `<command> > <owner>/.tmp/checks-<story-id>/<check>.log 2>&1; echo exit=$?`. `<check>` is the check's filesystem-safe name: `lint` for the lint command, and for a test seam its name as the story body gives it, lowercased, with every character outside `a-z`, `0-9` and `-` replaced by `-`. A green is its `exit=0` line; you read a log only by its tail (`tail -n 20 <log>`), never whole, and a fix-up implementer reads the log itself by its path. The story bead's notes gain no line: `branch:`, `review:` and `pr:` stay its only lines.

   **Evidence run.** After the marker is written, the checks run again on the integration branch tip; when a matching marker skipped the gate and the review, this is the run's first run of them. Either way, each check's command, its exit and the last twenty lines of its log are the PR's Evidence. A red run goes back to the fix-up implementer (spawned for it when the marker skipped the review), then its merger, for one more round, and the checks run again; the marker stays where the review left it, since a fix made here is unreviewed and a rerun reviews it; a second red run skips step 8 and goes to step 9, classified as step 6 says, with a `failed: <check> <command>` line in the report.

8. **Deliver.** First the **stray-commit check**, before any push: read every commit the push would carry but merges, `git -C <owner> log --no-merges --format='%H%x09%ae%x09%(trailers:key=Bead,valueonly,separator=%x2C)%x09%s' <default branch>..<branch>`, against the run's author, `git -C <owner> config user.email`. A commit with another author or no `Bead:` trailer came from outside the run (a test whose throwaway repo failed to init commits into the enclosing checkout): push nothing, skip the rest of step 8 and go to step 9 with one `failed: stray commit <sha> <subject>` line per such commit and no `PR:` line, classified as step 6 says. With a forge: push the integration branch's tip first (`git -C <owner> push -u origin <branch>`, as step 3 pushes before the draft), so the PR carries every merge. A refused push skips the rest of step 8 and goes to step 9 with a `failed: push <command>: <error>` line in the report and no `PR:` line, classified as step 6 says. Then open the draft if step 3 could not, and call the Skill tool with `mattpocock-skills:pr` to write the PR body, its Evidence from step 7's Evidence run (each check's command, exit and twenty-line tail), then append the sibling line (rebuilt as in step 3), and write the body back on stdin (`gh pr edit <n> --repo <forge-slug> --body-file -`, or `tea pr edit <n> --repo <owner> --description-file -`). Mark the PR ready (`gh pr ready <n> --repo <forge-slug>`, or drop the `WIP:` prefix with `tea pr edit <n> --repo <owner> --ready`), then `bd -C <owner> note <story-id> "pr: <url>"`. Then re-read every sibling story's notes (`bd -C <owner> show <sibling-id> --json`), and only then run step 3's sibling refresh. With no forge: push the integration branch when `<owner>` has an `origin` (`git -C <owner> push -u origin <branch>`; a refused push is the same `failed: push` line; with no `origin`, the branch stays local and the report names it); note `pr: <branch> <tip SHA>` (`git -C <owner> rev-parse <branch>`) on the story bead.

   The story bead stays **open**: `/dev:close-story` closes it after the PR merges. There is no Jira step here.

   If a `ready-for-human` ticket of the story is still open, the run ends in a **human stop** (step 9's report).

9. **Clean up** every worktree that is done with, this run's and earlier runs' alike. First `git -C <owner> worktree prune`, which drops the entries whose directory is already gone. Then sweep `git -C <owner> worktree list --porcelain` for every entry whose branch is `worktree-agent-*` or whose path is under `<owner>/.worktrees/` (a harness worktree, whose `branch` line reads `refs/heads/worktree-agent-<id>`, or a hand-rolled one; the rules doc's Worktrees), so a leftover from a cut-off run goes too. A locked one (a `locked` line in its entry) is left alone whatever its branch, and so are a `detached` one (no branch to test) and one whose branch is unmerged: each is reported with its path and the reason on the report's `worktrees:` line, never forced. The rest, whose branch is merged into `<branch>` (`git -C <owner> merge-base --is-ancestor <worktree branch> <branch>` exits 0; any other exit is unmerged), are removed: `git -C <owner> worktree remove <absolute path>` each. One the remove refuses (uncommitted changes in it) stays and goes on the line with git's error. Both `git -C <owner> worktree remove <absolute path>` and `git -C <owner> worktree prune` run with the sandbox disabled, as `/dev:close-story` step 4 runs the forge CLI: the sandbox denies deletes under `<owner>/.git/worktrees/` and no setting lifts that, so inside it the remove fails with `Operation not permitted` (or `could not lock config file .git/config`) and leaves the worktree registered, which is not a git error; a failure outside the sandbox is real and goes on the `worktrees:` line with its error. Each `ticket/<ticket-slug>` branch stays; a later run re-adds its worktree as the rules doc's hand-rolled fallback says. Then remove step 7's check logs, `rm -rf <owner>/.tmp/checks-<story-id>`. Leave `<owner>/.spec-notes/` in place.

   Final report, one block:

   ```
   story:   <story-id> <title>
   repo:    <owner>
   PR:      <url>            (or  branch: <name> @ <tip SHA>)
   failed:  <bead-id> <open blocker or failure reason>     (one per agent ticket left open,
            or <check> <command>                           or per check still red in step 7,
            or push <command>: <error>                     or the push step 8 could not make)
   human:   <bead-id> <title>                              (one per open ready-for-human ticket)
   waiting: <repo> <story-id>                              (each story whose text blocker names a human gate ticket)
   worktrees: <absolute path> <locked | detached | unmerged <worktree branch> | <error>>   (one per worktree step 9 left behind)
   resume:  <command>
   ```

   A run that skipped step 8 has no `PR:` line. The `failed:`, `human:`, `waiting:`, `worktrees:` and `resume:` lines appear only when they have content. `waiting:` comes from the "Stories" gather: each sibling story whose `## Blocked by` names one of the `human:` tickets. For a publish ticket, the `human:` line adds what the user does: merge this PR (or push the branch), publish `<crate> <version>`, and `bd -C <owner> close <bead-id> --reason "published <version>"`. `resume:` is `/dev:implement-spec <KEY>-<n>` (or `/dev:implement-spec <epic-id>` when the epic has no external ref) from the home (the workspace root for a cross-repo feature). Every ticket this run left open is unclaimed (steps 4 and 5), so the resumed run's `bd ready` lists it and its `failed twice:` note is the pointer; the one exception is a ticket on a `claimed by <actor>` line, whose claim bd refused to release. `bd -C <owner> unclaim <id>` is run by hand only when the orchestrator could not (the rules doc's Frontier, Unclaim): for that line, with `--force`, by a person who knows the actor is gone; and after a run that ended in an error instead of this report (an interrupted spawn, the rules doc's Cut-off agents), which leaves its running tickets `in_progress` (`bd -C <owner> list --parent <story-id> --status in_progress`), where the re-run's step 4 unclaims them itself and the hand run only brings them into `bd ready` sooner.

## Ticket runner brief

A ticket runner is a subagent, not a skill. Send this, filled in:

> You are the ticket runner for `<ticket-id>` in `<owner>` (story `<story-id>`, Jira `<KEY>-<n>` or none, integration branch `<branch>`, published version `<version>` if any; lint command `<lint>` or none; home `<home>`, a workspace session or a repo session). Read the rules doc, `<plugin root>/docs/agents/orchestration.md` (you are an orchestrator for this one ticket: you never edit files, and every change comes from a subagent you spawn) and the tracker doc, `<plugin root>/docs/agents/issue-tracker.md`, at "start work on a ticket". Every agent runs `bd` as `bd -C <owner>`, with one exception: step 3's inbox capture is plain `bd`, which reaches `<home>`'s database from where you run. You and the merger run `git -C <owner>` on the owner checkout; the implementer runs `git -C <worktree path>` on the hand-rolled route, and plain `git` in its own worktree under harness isolation, never `git -C <owner>`; a fix-up implementer runs `git -C <worktree path>` on either route. Absolute file paths, literal paths one command per Bash call (two exceptions: step 3's logged check call and step 4's lock wait), no `cd`; every brief you send carries the rules doc's absolute path above (and the tracker doc's when it points there), never a variable or a `~/` path, `<owner>`, the worktree path when there is one, that agent's `git` rule, as its first line the TMPDIR line when the agent works in a worktree (the rules doc's TMPDIR rule: the line, its `export` repeated per Bash call and its `mktemp -d` template), the lint command `<lint>` (or none), and the rules doc's Idle rule (every Bash call in the foreground, `timeout` up to 600000 ms, never a background call or a `Monitor`: a turn that ends with one still running sends an interim report in place of the real one), and a brief to an agent that commits or merges also carries the rules doc's Commits rule (retry a hook-rejected commit before any other `git` operation; merge only onto a clean tree). The Idle rule binds you too. Spawn each subagent with an explicit `model:`, then end your turn: its report arrives as the Agent tool's completion notification and resumes you (the rules doc's Waiting: an Agent call returns at once, there is no foreground spawn, and you never poll). First check that you have the Agent tool: without it, report `<ticket-id> failed: no Agent tool` now and stop (the rules doc's Subagent type).
>
> A subagent that returns an API error, or ends with no report, is replaced by a fresh subagent at the same model in the same worktree (the rules doc's Cut-off agents): an implementer's replacement is briefed as the fix-up implementer in step 3, no reset, with the ticket as its pointer, since its commits are on the branch.
>
> 1. `bd -C <owner> update <ticket-id> --claim`. Read its `complexity:` tier.
> 2. Spawn the **implementer** at the tier's implementation model. Worktree: `isolation: "worktree"` when `<owner>` is your session's repo; otherwise make `git -C <owner> worktree add <owner>/.worktrees/<ticket-slug> -b ticket/<ticket-slug> <branch>` (reuse the worktree if it exists; if only the branch survives an earlier run, re-add it as the rules doc's hand-rolled fallback says) and give its absolute path in the brief. The brief starts with the TMPDIR line (on the harness route the implementer fills in the path `pwd` prints). The implementer resets its worktree onto `<branch>`'s tip first; calls the Skill tool with `mattpocock-skills:tdd` to build the ticket; passes `timeout: 600000` on every lint and test run (the brief's lint command, then the owner repo's test commands, leaving out any the lint command already runs, such as `make ci`, `make fixtures` or `scripts/test-*.sh`; the rules doc's Idle rule: at the 120-second default a longer call is moved to the background); commits with `Bead: <ticket-id>` and `Refs: <KEY>-<n>` trailers (`Bead:` alone with no key); bails out with `bd -C <owner> note` and `needs split` plus a proposed cut when edits spread beyond what the ticket names or a third red-green cycle hits the same seam; merges `<branch>`'s tip into its branch before reporting; and reports its branch name and worktree path. For `medium` and `high` it reports *ready for review*. The implementer runs no gate and spawns no one; it is then done, and nothing is sent back to it.
> 3. **Check and review loop**, every tier, after the implementer reports and before the merger, as the rules doc's Check gate says: the checks, then the review, one loop. You run the story's checks yourself, read-only, in the worktree path and on the branch the implementer reported (it has `<branch>`'s tip merged): the lint command `<lint>` first, run in the worktree (`make lint` as `make -C <worktree path> lint`, as step 7 runs it with `make -C <owner>`; none: skipped), then each test seam the story bead's `## Test seams` section names (`bd -C <owner> show <story-id>`), leaving out any the lint command already runs, each check through its tool's directory flag or an absolute path under `<worktree path>` (`make -C <worktree path> lint`, `<worktree path>/scripts/test-foo.sh`, `cargo test --manifest-path <worktree path>/Cargo.toml`), as step 7's Running the checks does with `<owner>`; the first red stops the run. Each check is one foreground Bash call with `timeout: 600000`, both streams to a log and the exit code echoed, `mkdir -p <worktree path>/.tmp; export TMPDIR=<worktree path>/.tmp; <check> > <worktree path>/.tmp/checks-<round>-<k>.log 2>&1; echo exit=$?` (`<k>` the check's place in that order; this compound call is an exception to one command per Bash call, as the merger's `until` loop is), so a green costs you one `exit=0` line and no check output enters your context; you never read a log whole. Red: read `tail -n 40 <log>` (longer than step 7's twenty-line tail, which feeds the PR's Evidence: here the tail is your diagnosis of the red), and note `bd -C <owner> note <ticket-id> "checks <round>: red <command>"` (a green writes no note). A red spawns a fresh fix-up implementer and the loop starts over from the checks. The **fresh fix-up implementer** runs at the tier's implementation model in the same worktree and on the same branch, briefed as the blocking fix-up below with a pointer-only brief: the ticket id, the worktree path and branch, the failing command, the log path, and no pasted output (the TMPDIR line first, as every worktree brief). The budget is three fix-ups of either cause; the fourth red or blocking verdict is `failed`. `<round>` counts both causes, 1 for the first run of the checks and up by one after each fix-up, the number a `review <round>:` note carries too. Green: a `low` ticket exits the loop, go to step 4; for `medium` and `high`, spawn a **reviewer** at the tier's review model, briefed to call the Skill tool with the built-in `code-review` (effort `medium` or `high`) on the implementer's changes since `<branch>`, with its standards sources spelled out: those searched in `<owner>` (its `CODING_STANDARDS.md` or `CONTRIBUTING.md`, `GLOSSARY.md` and `docs/adr/` where they exist) plus `<plugin root>/docs/agents/coding-standards.md` spelled as the path this session resolved, which the skill never finds on its own, and to report findings only, every finding tagged **blocking** or **minor** (blocking: an acceptance criterion unmet, a behaviour wrong or a test missing; minor: wording, naming or a nit that changes no behaviour an acceptance criterion names), the report ending on one line, `verdict: clean` when no finding is blocking, else `verdict: blocking (<n>)` with the count. On the hand-rolled route name the diff, `git -C <owner> diff <branch>...ticket/<ticket-slug>`, and the worktree path. Write the findings and the verdict on the ticket, `bd -C <owner> note <ticket-id> "review <round>: <findings>; <verdict line>"`, then act on the verdict as the rules doc's Review verdict says. **Blocking**: a blocking verdict spawns a fresh fix-up implementer and the loop starts over from the checks, never straight to the reviewer; that fix-up implementer is pointed at that note. It works in the worktree path and on the branch name the implementer reported, with no `isolation` (that would open a new worktree on a new branch) and `git -C <worktree path>` on either route; its brief starts with the TMPDIR line for that worktree; it does not reset the worktree (the commits it fixes are there), and otherwise follows step 2: `tdd`, `timeout: 600000` on every lint and test run, the same trailers and bail-out, `<branch>`'s tip merged before it reports. A fresh fix-up implementer per fix-up, the same worktree throughout, within the budget above. The minors fix-up spends no budget and advances no round. **Clean** exits the loop, minors or none: no reviewer runs again. The minors go to one last fix-up implementer, briefed as above, before the merger; those you judge out of the ticket's scope go instead to the inbox as the tracker doc's "capture a retro item" says (plain `bd`, the one exception above; that section's command, labels and target label for your session mode, `<KEY>-<n>` as the external ref when there is a key, the finding and the ticket id as the body's Moment) and never to a bead of the story. Either way, go to step 4. Never resume an earlier implementer with `SendMessage` (the rules doc's Orchestrator role: its reply would land in the top-level session and your turn would already be over).
> 4. Spawn a **merger** at the tier's implementation model; its brief starts with the TMPDIR line for the implementer's worktree, since it runs the story's checks there and in `<owner>`. It first merges `<branch>`'s current tip into the implementer's branch (`git -C <worktree path> merge <branch>`) and runs the story's checks there, the lint command `<lint>` included, so the integration merge itself is short; every lint and test run, there and in `<owner>`, passes `timeout: 600000` as step 2 says. Then it takes the owner checkout, one merger at a time: while `<owner>/.git/index.lock` or `<owner>/.git/MERGE_HEAD` exists, another merger holds it, so it waits in one foreground Bash call, `until ! [ -e <owner>/.git/index.lock ] && ! [ -e <owner>/.git/MERGE_HEAD ]; do sleep 5; done` with `timeout: 300000` (the one shell wait, the rules doc's Waiting; never a background call or a `Monitor`), and never removes a lock itself; a call that `timeout` ends means the lock never cleared. Holding it, it confirms `git -C <owner> branch --show-current` is `<branch>`, runs the **stray-commit check** on what the merge brings in (`git -C <owner> log --no-merges --format='%H%x09%ae%x09%(trailers:key=Bead,valueonly,separator=%x2C)%x09%s' <branch>..<implementer branch>`: a commit whose author is not `git -C <owner> config user.email`, or with no `Bead:` trailer, stops it unmerged with `failed: stray commit <sha> <subject>`, which you report as `<ticket-id> failed: stray commit <sha> <subject>`), merges the implementer's branch (`git -C <owner> merge <implementer branch>`), resolves conflicts, and reruns the story's checks on the merged result in `<owner>`, the lint command `<lint>` included. If passing needs real code changes it reports that instead, and you send them to a fresh fix-up implementer briefed as in step 3, then merge again.
> 5. `bd -C <owner> close <ticket-id>`.
>
> Report exactly one line: `<ticket-id> closed`, `<ticket-id> needs split: <proposed cut>`, or `<ticket-id> failed: <reason>`. Anything you cannot finish (a fourth red or blocking verdict, a merger that cannot merge or times out on the lock) is `failed` with that reason.
