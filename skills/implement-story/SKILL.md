You have been given a **story** bead id: the part of one feature that lands in one repo, parent of that repo's tickets. The issue tracker rules are in `${CLAUDE_PLUGIN_ROOT}/docs/agents/issue-tracker.md`.

The goal is the story implemented on a single **integration branch** in its owner repo, every `ready-for-agent` ticket closed after its own review, the story reviewed as a whole at the story gate, and delivered as a PR (or, with no forge, the branch).

The tickets are not a list of steps. They are a **task graph** with blocking relationships between them, so there is always a **frontier** of tickets ready to be grabbed.

## Shared rules

The session running this skill is the **story orchestrator** and follows `${CLAUDE_PLUGIN_ROOT}/docs/agents/orchestration.md`: Orchestrator role, Scratch space, Complexity tier and Frontier, with the harness mechanics in `${CLAUDE_PLUGIN_ROOT}/docs/agents/harness.md`. Read both before step 1. "The tier's model", "the frontier", "human stop" and "stall" below mean those sections. Communication to and from subagents goes through context pointers (story bead, ticket beads, notes, commits), never copies.

## Owner repo

`<owner>` is the absolute path of the story's owner repo: the session's repo (`git rev-parse --show-toplevel`) when `/dev:implement-story` is typed there, else the path in the brief that spawned you. The procedure below is the same either way, with the repo as its parameter:

- every `bd` command, by every agent, is `bd -C <owner> …`, with one exception: the inbox capture of a deferred finding (step 7, and the ticket orchestrator brief's step 3) is plain `bd`, which reaches `<home>`'s database from where every agent runs, as the tracker doc's "capture a retro item" says;
- `git` follows where the agent works. You and a ticket orchestrator run `git -C <owner> …` on the owner checkout (a ticket orchestrator also `git -C <worktree path>` read-only on its ticket's worktree). An implementer on the hand-rolled route runs `git -C <worktree path> …`. A harness-isolated implementer runs plain `git` in its own worktree, which is its working directory; `git -C <owner>` would put its commits straight onto the integration branch;
- every file path is absolute, under `<owner>` or the agent's worktree; the shell stays where it started and never `cd`s;
- paths are spelled out literally, one command per Bash call, as the harness doc's Scratch space says (Literal paths);
- every forge command names the repo (step 3);
- every brief to a subagent carries `<owner>`, the worktree path when it has one, and the `git` rule for that agent;
- every brief to an agent that works in a worktree (an implementer, one on a fix-up among them) starts with the **TMPDIR line** of the harness doc's TMPDIR rule, `mkdir -p <worktree>/.tmp && export TMPDIR=<worktree>/.tmp` with the worktree path spelled out (on the harness route the implementer fills in the path `pwd` prints), and its two riders: `export TMPDIR=<worktree>/.tmp;` repeated at the head of every Bash call that runs `mktemp`, a heredoc or a script, and `mktemp -d <worktree>/.tmp/<name>.XXXXXX` in place of a bare `mktemp -d`, which macOS runs under `/var/folders` whatever `TMPDIR` says;
- every brief that points at a doc under `<plugin root>/docs/agents/` (orchestration.md, harness.md, issue-tracker.md, coding-standards.md, any other) spells its absolute path literally, `<plugin root>/docs/agents/<doc>.md` with `<plugin root>` replaced by the path this session resolved (the rules doc's Plugin root rule), never an environment variable and never a `~/` path: a subagent's Bash has no such variable. A pointer such as "the harness doc's Idle rule" in a brief names that doc by the same absolute path, which the ticket orchestrator brief below states once.

`<owner>` outside `~/src`, when it is not the session's repo, makes `bd` and `git` writes fail with `Operation not permitted`: the tracker doc's "bd writes outside the session's repo" says what to do. The session mode, `<home>` and `<workspace>` are as **the one test** in the tracker doc's opening defines them: `<home>` is the session's repo, the workspace for a spawned story orchestrator and the owner repo for a typed one, and plain `bd` reaches its database. Typed in an owner repo, the session is a repo session with no workspace, and what needs another database degrades: the sibling line, the sibling refresh with step 8's sibling re-read (step 3), and the `waiting:` line (step 9) are skipped, and a text blocker in another repo cannot be read, so it counts as open (the Frontier section's unreadable-blocker rule). A story cut in such a repo session runs right there. Only a story whose text blocker is in another repo is run from the workspace session: its wait message says to run `/dev:implement-spec <KEY>-<n>` (or `/dev:implement-spec <epic-id>` when the epic has no external ref) from the workspace root (`/dev:implement-story <story-id>` typed there would take `<owner>` for the workspace and not find the story).

`<KEY>-<n>` is the story's `external_ref`. A story without one has no key: its commits carry `Bead:` alone (no `Refs:`), and the sibling line (`<repo> <story-id> <url>`) and the Jira context below are skipped; its branch is `feat/<story-id>`, as every story's is (step 3).

`<ticket-slug>` is the ticket id; `<epic-id>` is the epic bead id on the story's `## Parent` line. **Worktrees**: harness isolation (`isolation: "worktree"`) makes worktrees only in the session's repo, so a subagent working in `<owner>` takes it only when `<owner>` is the session's repo. Otherwise its worktree is hand-rolled inside `<owner>`, as the harness doc's fallback: `git -C <owner> worktree add <owner>/.worktrees/<ticket-slug> -b ticket/<ticket-slug> <integration branch>` (reused if it exists; when only the branch survives, re-add it as the harness doc's fallback says), and the brief gives its absolute path.

## Steps

1. **Read the story and its tickets.** `bd -C <owner> show <story-id> --json` (an array; `.[0]`). Refuse with one line and create nothing when:
   - the bead is an epic whose direct children (`bd -C <owner> children <id> --json`) include a non-story bead: `<id> refused: flat epic (tickets directly under the epic bead); the story skills do not handle it — the small-bug path does: /mattpocock-skills:implement <ticket-id> per ticket, then bd close <epic-id>`;
   - otherwise the bead is not of `issue_type` `story`: `<id> is of type <type>, not a story; /dev:implement-story takes a story bead id.`

   The tickets are `bd -C <owner> children <story-id> --json`. The story's **tier** is the max `complexity:` label among them. The story's notes (`.[0].notes`) are what earlier runs left behind, one line each: `branch:` (step 3), `review:` and `story review <round>` (step 7) and `pr:` and `delivered:` (step 8); read them once here, the last line of a kind winning. A story is **finished** when every child is `closed` or carries `ready-for-human`, `needs-triage` or `wontfix` (the rules doc's Frontier, Deferrals) and its notes carry a `pr:` line: touch nothing, and go straight to the final report (step 9) with the `pr:` and `branch:` lines read from the notes. The one write it may make: a finished story with no `delivered:` line (delivered before step 8 wrote one) gets it now, step 8's note on the branch's current tip, so `/dev:implement-spec` can review it.

   **Merge guard.** The guard covers a delivered story with an open `ready-for-agent` ticket: one whose notes carry a `pr:` line, a URL or step 8's `<branch> <tip SHA>` form, while a child that is not closed (open, in_progress or blocked) is labelled `ready-for-agent` (a ticket added after the first delivery, ADR 0011's add mode). A URL goes to one forge query; the branch form or no forge is decided locally first, then asked (below). The query decides, with the forge decided as step 3 says (its remote pre-check and proof run here first), run with the sandbox disabled, as `/dev:close-story` step 4 does: `gh pr view <url> --json state`, or `tea api --repo <owner> repos/{owner}/{repo}/pulls/<n>` and its `"merged"` and `state` fields (a Forgejo `state` reads `closed` for merged and unmerged alike). MERGED: refuse with `<story-id> refused: PR <url> already merged; the new ticket belongs in a new story: run /dev:spec-to-stories <KEY>-<n> in add mode (or /dev:spec-to-stories <epic-id> when the epic has no external ref); then close <ticket-id> (moved to the new story)` and create nothing; the line names each open `ready-for-agent` ticket as `<ticket-id>`, which stays open under the merged story until add mode has carried its work into a new story, so close it there then (`/dev:close-story` cannot). CLOSED unmerged: refuse with `<story-id> refused: PR <url> is closed unmerged` and create nothing. OPEN: continue on the `branch:` note's branch, the re-delivery path of steps 3 and 8. When the forge cannot tell (no forge, or a branch-form `pr:` note), decide the branch form locally first: `git -C <owner> fetch origin` (skipped with no `origin`), then `git -C <owner> merge-base --is-ancestor <tip SHA> origin/<default branch>` (exit 0: as MERGED; exit 1: as OPEN; a failed fetch of an existing origin or any other exit: it cannot decide (ask)); find `<default branch>` as step 3 says; with no `origin`, compare against the local `<default branch>`. Ask the user only when that cannot decide, whether the PR, or for the branch form the branch, has merged into the default branch, and wait for the answer. In a run spawned by `/dev:implement-spec`, which has no user (the rules doc's Delivery), end instead with `failed: <story-id> merge state unknown (<pr: value>): say whether it merged, then re-run` and create nothing. A failing forge command is an error, reported as `<story-id> refused: forge check failed: <error>`, never as "no forge".

   Read the story's `## Blocked by` lines and check each as the Frontier section says (a blocker naming a story reads like any bead: open until `/dev:close-story` closes it). While any is open, no ticket can start: report `<story-id> waits on <repo> <bead-id> <title>` for each (a story blocker adds `merge its PR and run /dev:close-story <blocker-id>`; in a repo session, a blocker in another repo cannot be read: show its line as written in place of the title, and add `run /dev:implement-spec <KEY>-<n> from the workspace root`, or `/dev:implement-spec <epic-id>` when the epic has no external ref), and stop before any branch or commit exists.

2. (optional) Use an **exploration subagent** for any exploration the tickets need. Its brief names the story bead and `<owner>`; it reads the story's design field first (`.[0].design` of its own `bd -C <owner> show <story-id> --json`), the story cut's orientation for this repo, and writes its own notes into `<owner>/.spec-notes/<epic-id>/`, the directory this skill alone owns (the rules doc's Scratch space); every later brief points there by that absolute path.

3. **Integration branch.** A `branch:` line in the story's notes means an earlier run made it: `git -C <owner> switch <name>` if the owner checkout moved off it, and keep any draft PR it opened. Otherwise find the default branch (`git -C <owner> symbolic-ref --short refs/remotes/origin/HEAD` minus `origin/`; with no `origin/HEAD`, whichever of `main` and `master` exists), then `git -C <owner> switch -c feat/<story-id> <default branch>` (the branch is named `feat/<story-id>`, keyed or not: the key stays on commits, the PR body and the bead) and `bd -C <owner> note <story-id> "branch: <name>"`. The owner checkout stays on the integration branch until the run ends; each ticket orchestrator lands its ticket onto it there.

   Apply the rules doc's Gitignore rule on the integration branch: append each missing entry with one shell command (`printf '%s\n' /.claude/worktrees/ >> <owner>/.gitignore`, and so on). Then, when `git -C <owner> status --porcelain -- .gitignore` prints anything, the file is dirty: with an entry appended here, or with one an earlier run appended and was cut off before committing. When every added line in `git -C <owner> diff -- .gitignore` (every line of the file, when it is untracked) is one of the rule's four entries and no line is removed, commit it: `git -C <owner> add <owner>/.gitignore` and `git -C <owner> commit -m "chore: ignore agent scratch space" --trailer "Bead: <story-id>" --trailer "Refs: <KEY>-<n>"` (no `Refs:` with no key). Any other line is an edit of the user's, which the harness doc's Commits rule would stop at the first merge: end the run now with `failed: <owner>/.gitignore has uncommitted edits; commit or stash them and re-run`, and a switch above that git refused over that file ends the run the same way. This is the repo plumbing the Orchestrator role allows; it is never done with `Edit` or `Write`.

   **Check command.** Resolve the check command **once per run**, here, with the owner checkout on the integration branch: `make check`, since every owner repo has a `check` target (the rules doc's Check command); with none, end the run now with `failed: no check target in <owner>; run /dev:setup-repo there, then re-run`, before any ticket orchestrator starts. Ask make whether it has one, never grep a Makefile: `make -C <owner> -pRrq : 2>/dev/null | awk '/^# Not a target:/{n=1;next} /^check::?([^=:]|$)/&&!n{c=1; if (/^check::? *[^ :]/) f=1} c&&/^#  (commands|recipe) to execute/{f=1} /^$/{c=0} {n=0} END{exit !f}'` prints GNU make's database without running the `check` recipe (parsing still expands `$(shell ...)`, and a makefile with a rule to remake it is remade, as on any make call), so it finds a `check` target in `GNUmakefile`, `makefile` or `Makefile`, in an included file, or as one of several targets in a rule, and exits 0 when there is one with prerequisites or a recipe; a `check:=` variable is listed as `check := ...`, never as a target, a `check` named only in `.PHONY` is listed with neither prerequisites nor a recipe, and a missing Makefile prints no database and exits 1, so all three read as no check target. The result, `<check command>`, is `make check`: every ticket orchestrator brief carries it in its header and step 7 gates on it, so every ticket of the run, parallel siblings included, is gated by the same command even when one of them adds or drops a `check` target mid-run. Each invocation resolves it here, a re-typed one included; a `resume:` line (step 4's Resumed) keeps the one already resolved.

   Decide **once** which forge fronts the repo (already decided in step 1 when the merge guard ran). Pre-check `git -C <owner> remote get-url origin`: `github.com` → `gh`; a Forgejo/Gitea host → `tea`; a plain `ssh://host/path.git`, a bare path, or no remote → none. Both CLIs otherwise act on the working directory's repo, so every forge command names its repo: `gh … --repo <forge-slug>`, with `<forge-slug>` the `owner/name` part of that repo's `origin` URL; `tea … --repo <path>`, which takes the repo's absolute path and finds the remote and login from it. For the owner repo that is `<forge-slug>` of `<owner>` and `--repo <owner>`. Prove the forge with `gh repo view <forge-slug>` or `tea pr list --repo <owner> --limit 1`. Forge CLIs keep their tokens outside the sandbox, so inside it they fail with `unable to get or create config file`, which is not a missing login: run each forge command with the sandbox disabled. A failure outside the sandbox is real (`no available login` → the user runs `gh auth login` or `tea login add`): stop and report it.

   With a forge, open a **draft PR** after the first batch (step 4) that contains a `closed` report (a branch with no commits ahead of the default branch cannot open one). The ticket orchestrators' merges are local, and naming `--head` stops `gh` pushing for you, so first run step 8's **stray-commit check** (a hit ends the run there, as step 8 says), then **push** the integration branch, `git -C <owner> push -u origin <branch>`, on the typed command's authority (the rules doc's Delivery); a refused push leaves the draft unopened for now, the frontier is worked on (the merges are local), and step 8 pushes again. With the branch pushed, `gh pr create --draft --repo <forge-slug> --head <branch> --base <default branch> --title "<story title>" --body-file -`, or `tea pr create --repo <owner> --head <branch> --base <default branch> --title "WIP: <story title>" --description "<body>"` (Forgejo treats the `WIP:` prefix as draft). Its body names the story, the Jira key, and one **sibling line** `Part of <KEY>-<n>:` listing the sibling stories: every other `story` bead carrying `<KEY>-<n>` in the manifest's repos (the "Stories" gather in the tracker doc, whose `--json` output carries each sibling's notes). Each sibling appears as `<repo> <story-id> <url>`, the url taken from its `pr:` note; with no `pr:` note, from its draft PR looked up by its `branch:` note in `<workspace>/<repo>`. A sibling's forge is decided from its own `git -C <workspace>/<repo> remote get-url origin`, as above for the owner: `gh pr list --repo <its forge-slug> --head <branch> --json url -q '.[0].url'`, or `tea pr list --repo <workspace>/<repo> --state open --fields head,url --output json` filtered on `head`. Only when neither exists (a sibling with no forge, or no draft yet), `<repo> <story-id> <branch>`. Then run the **sibling refresh**: in each sibling's open PR, regenerate the whole `Part of <KEY>-<n>:` block from the Stories gather's current notes on every run, listing every story of the feature but that sibling, this story's PR included, and never patch single lines. Both edit commands replace the whole body, so read it first and write all of it back on stdin, with the sibling's own CLI and repo: `gh pr view <n> --repo <its forge-slug> --json body -q .body` then `gh pr edit <n> --repo <its forge-slug> --body-file -`, or `tea api --repo <workspace>/<repo> repos/{owner}/{repo}/pulls/<n> | jq -r .body` then `tea pr edit <n> --repo <workspace>/<repo> --description-file -`. A sibling with no forge or no open PR is skipped. With no forge the integration branch *is* the deliverable; a request for a PR is answered with the branch name.

4. **Work the frontier.** A ticket of the story that is `in_progress` while no ticket orchestrator of this run holds it was claimed by a cut-off run (the harness doc's Cut-off agents): `bd -C <owner> unclaim <id>` each first. An unclaim bd refuses because another actor holds the claim is never forced: the ticket is off this run's frontier, with `failed: <id> claimed by <actor>` in step 9's report. Then `bd -C <owner> ready --parent <story-id> -n 0 --json`, keeping only the tickets labelled `ready-for-agent` (the rules doc's Frontier: `bd ready` lists a `ready-for-human` or `needs-triage` child all the same) and minus the tickets that failed twice in this run (step 5; a twice-failed ticket is open and unclaimed, so `bd ready` lists it, and only this run's count keeps it off). Step 1 already cleared the story's text blockers. Spawn one **ticket orchestrator** per frontier ticket with `subagent_type: "general-purpose"` (the rules doc's Subagent type) at `model: opus`, the whole current frontier as one parallel batch in one message, then end your turn: each ticket orchestrator's report line arrives as the Agent tool's completion notification and resumes you (the harness doc's Waiting: an Agent call returns at once, and you never poll). Fill the brief below. Spawn nothing else per ticket: the ticket orchestrator owns the ticket's implementer, its reviewer and its landing.

   **Resumed.** A `resume:` line from the epic orchestrator means the batch in flight was cut off and its agents stopped: re-read the story's notes as step 1 does (`branch:`, `review:`, `story review <round>`, `pr:`), keep the check command step 3 resolved, confirm the owner checkout is on the integration branch (step 3), and go to step 6, where the unclaim above returns the cut-off tickets to the frontier. An invocation that was cut off is re-typed by the user and takes the same path from step 1.

   When a text blocker is a publish ticket (titled `publish <crate> <version>`), the brief also carries the published version: the version in that blocker's `close_reason` (written `published <version>`), which wins over the version in any title. No version in the reason → ask the user for it and wait.

5. **Act on every report of the batch**, each as its notification resumes you. Each ticket orchestrator reports one line:
   - `<id> closed`: nothing more for that ticket. The first batch with one opens the draft PR (step 3).
   - `<id> needs split: <cut>`: create the proposed beads as children of the story, each `bd -C <owner> create --parent <story-id> --labels complexity:<tier>,ready-for-agent --deps blocked-by:<new-id>,... "<title>" --body-file -` with the edges and the tier the cut proposes for that bead (else the original's tier); move every bead the original blocked onto the new ones (`bd -C <owner> dep add <dependent> <new-id>`, so a publish ticket still waits on all of the story's work); close the original with `bd -C <owner> close <id> --reason "split into <ids>"`.
   - `<id> failed: <reason>`: the ticket orchestrator ended without closing its ticket, and its claim outlives it (the rules doc's Frontier, Unclaim), so first `bd -C <owner> unclaim <id>` (a refusal follows step 4's rule). A first failure gives it one fresh ticket orchestrator in the next batch with the reason added to its brief. A second failure takes the ticket off the frontier for this run: `bd -C <owner> note <id> "failed twice: <reason>; resume: <command>"` with step 9's resume command, so the ticket stands open and unassigned, `bd -C <owner> ready --parent <story-id>` lists it, and a resumed run finds the pointer; it is a `failed:` line in step 9's report. An API error in place of a report line is a cut-off, not a failure: the ticket rejoins the frontier at step 6 through step 4's unclaim, its failure count unchanged.

6. **Re-evaluate the frontier** once every report of the batch has arrived and been handled, and spawn the next batch from it (step 4). Repeat until a batch would be empty. Then:
   - every child is `closed` or carries `ready-for-human`, `needs-triage` or `wontfix`, what step 1 counts as finished short of the `pr:` note → steps 7 and 8. A child carrying one of those labels is not waited for (the rules doc's Deferrals);
   - otherwise skip steps 7 and 8 and go to step 9. The run is a **human stop** if a `ready-for-human` ticket of the story is open and a **stall** otherwise, as the rules doc says; either way the report names each other child left open.

7. **Story gate.** The story gate is the rules doc's Check gate loop on the integration branch tip, the story row of the rules doc's table: it exits when the checks are green on the tip the review called clean. The check command is the one step 3 resolved for the run, the one every ticket orchestrator brief carried. Each pass runs the checks first, read from the check records (the rules doc's Check record and Check scope). First confirm `git -C <owner> branch --show-current` prints `<branch>` and confirm the owner checkout is clean, `git -C <owner> status --porcelain` prints nothing (untracked files count, since the check runs on the working tree while the record keys on the committed tree); else skip step 8 and go to step 9 with `failed: <story-id> not on <branch>` or `failed: <story-id> owner checkout dirty: <files>`, `<files>` the paths that status call printed, classified as step 6 says. Then read the tip's tree, `git -C <owner> rev-parse <branch>^{tree}`, as `<tree>`: its record is `<owner>/.tmp/checks/<tree>/record`, and a tree with a record is checked: read its exit and run nothing, whichever orchestrator wrote it (a ticket orchestrator's record of the tree it last landed is the common case). Otherwise run the check command read-only on the owner checkout, which is on `<branch>`, in one foreground Bash call with `timeout: 600000` (the harness doc's Idle rule) that writes the record: the ticket orchestrator brief's step 3 check-record call with `<owner>` as its `<worktree path>`, the one compound call that writes a record, so a green costs you one `exit=0` line and you never read a log whole; a red is read by `tail -n 40 <log>`, `<log>` the record's log. With the checks green, compare the story's `review:` note with the tip, `git -C <owner> rev-parse <branch>`: the same SHA exits the gate. The story keeps the reviewed tip in its notes: its `review:` note names the tip the gate exits on after a clean review, so a rerun reviews only a tip that has moved past it (a ticket landed since, in add mode or after a split, or a fix-up). No note, or a tip that has moved since, means the review is due: call the Skill tool with `mattpocock-skills:code-review` on the integration branch since the default branch in `<owner>`, with its two sub-agents run at the review model of the story's tier (one tier up, the rules doc's trust rule 1). The skill reviews the working directory's repo, so the invocation names `<owner>` and spells out what its sub-agents receive: the base SHA `<base>`, `git -C <owner> merge-base <default branch> <branch>`, the diff `git -C <owner> diff <base>..<branch>` and the commit list `git -C <owner> log <base>..<branch> --oneline`, for context; the two axes, as the rules doc's Review scope says, where the spec axis is the story's body (`bd -C <owner> show <story-id>`: what it delivers and its `## Test seams`, where its criteria must be exercised), with the Jira epic `<KEY>-<n>` for the feature context, and the standards axis is what entered since the ticket reviews: the conflict resolutions and the coherence across tickets, plus this gate's fix-up commits since the last story review (each ticket's own diff was reviewed at its row and is not read for standards again), each handed over as a command: every merge's resolution, `git -C <owner> show --remerge-diff <merge>` for each `<merge>` of `git -C <owner> log --merges --format=%H <base>..<branch>` (it prints only what the merge resolved by hand), and the fix-up commits, `git -C <owner> log --no-merges --grep='^Bead: <story-id>$' <since>..<branch>` with `-p` (a fix-up commits under the story's id, a ticket's implementer under the ticket's), `<since>` the tip the last `story review` note names, else `<base>`, read against the standards sources searched in `<owner>` (its `CODING_STANDARDS.md` or `CONTRIBUTING.md`, `GLOSSARY.md` and `docs/adr/` where they exist) plus `<plugin root>/docs/agents/coding-standards.md` spelled as the path this session resolved (the bullet above), which the skill never finds on its own; and the shape of each sub-agent's report, as the rules doc's Review verdict says: every finding tagged **blocking** or **minor**, the last line `verdict: clean` or `verdict: blocking (<n>)`. Its sub-agents report findings only and create no bead. Write the findings and the verdict on the story, `bd -C <owner> note <story-id> "story review <round> <tip SHA>: <findings>; <verdict line>"`, `<tip SHA>` the tip the review read and `<round>` one more than the last `story review` note's round step 1 read (1 when there is none), so a rerun numbers on rather than restarting. A red or a blocking verdict goes to a fresh implementer by pointer brief and the loop starts over, from the checks; its fix-up moves the tip off any `review:` note, so the next green pass is reviewed again. **Clean** ends the review, minors or none: the minors go to one last implementer on a fix-up, and the minors fix-up reruns the checks and spends no budget. Once it has landed (or the review found nothing to fix), write the reviewed tip, `bd -C <owner> note <story-id> "review: <tip SHA>"` with the tip re-read (`git -C <owner> rev-parse <branch>`), and the loop starts over, so its next green pass exits; a red there goes to a fresh fix-up like any other, whose new tip the gate reviews.
