You have been given a **story** bead id: the part of one feature that lands in one repo, parent of that repo's tasks. The issue tracker rules are in `${CLAUDE_PLUGIN_ROOT}/docs/agents/issue-tracker.md`.

The goal is the story implemented on a single **integration branch** in its owner repo, every `ready-for-agent` task closed when it lands, the story reviewed as a whole at the story gate, and delivered as a PR (or, with no forge, the branch).

The tasks are not a list of steps. They are a **task graph** with blocking relationships between them, so there is always a **frontier** of tasks ready to be grabbed.

## Shared rules

The session running this skill is the **story orchestrator** and follows `${CLAUDE_PLUGIN_ROOT}/docs/agents/orchestration.md`: Orchestrator role, Scratch space, Complexity tier, Frontier and Repo plumbing and Cut-off probe, with the harness mechanics in `${CLAUDE_PLUGIN_ROOT}/docs/agents/harness.md`. Read both before step 1. "The tier's model", "the frontier", "human stop" and "stall" below mean those sections. Communication to and from subagents goes through context pointers (story bead, task beads, notes, commits), never copies.

## Owner repo

`<owner>` is the absolute path of the story's owner repo: the session's repo (`git rev-parse --show-toplevel`) when `/dev:implement-story` is typed there, else the path in the brief that spawned you. The procedure below is the same either way, with the repo as its parameter:

- every `bd` command, by every agent, is `bd -C <owner> …`, with one exception: the inbox capture of a deferred finding (step 7, and `/dev:task-orchestrator`'s **Check gate**) is plain `bd`, which reaches `<home>`'s database from where every agent runs, as the tracker doc's "capture a retro item" says;
- `git` follows where the agent works. You run `git -C <owner> …` on the owner checkout, and you alone write there: a task orchestrator never touches it (it runs `git -C <worktree path>` read-only on its task's worktree, and on the hand-rolled route only `git -C <owner> worktree add`). An implementer on the hand-rolled route runs `git -C <worktree path> …`. A harness-isolated implementer runs plain `git` in its own worktree, which is its working directory; `git -C <owner>` would put its commits straight onto the integration branch. An implementer spawned without `isolation` into a worktree another reported (a later story-level fix-up, a conflict resolution) runs `git -C <worktree path> …` on either route;
- every file path is absolute, under `<owner>` or the agent's worktree; the shell stays where it started and never `cd`s;
- paths are spelled out literally, one command per Bash call, as the harness doc's Scratch space says (Literal paths);
- every forge command names the repo (the rules doc's Repo plumbing and Cut-off probe, its Forge decision);
- every brief to a subagent carries `<owner>`, the worktree path when it has one, and the `git` rule for that agent, except the short task orchestrator brief (Task orchestrator brief, below), whose `git` rule `/dev:task-orchestrator` states itself;
- every brief to an agent that works in a worktree (an implementer, one on a fix-up among them) starts with the **TMPDIR line** of the harness doc's TMPDIR rule, `mkdir -p <worktree>/.tmp && export TMPDIR=<worktree>/.tmp` with the worktree path spelled out (on the harness route, whose brief carries no path, two steps: the implementer's first Bash call is `pwd` alone, and the path it printed is spelled literally in every later `export`, never `$PWD`, which the worktree guard refuses), and its two riders: `export TMPDIR=<worktree>/.tmp;` repeated at the head of every Bash call that runs `mktemp`, a heredoc or a script, and `mktemp -d <worktree>/.tmp/<name>.XXXXXX` in place of a bare `mktemp -d`, which macOS runs under `/var/folders` whatever `TMPDIR` says; and next to it the plain-command line, one plain `git` or `bd` command per Bash call, every path spelled out, the harness doc's Literal paths stated inline, since inside a harness worktree a brief that only cites it leaves the worktree guard refusing calls;
- every brief that points at a doc under `<plugin root>/docs/agents/` (orchestration.md, harness.md, issue-tracker.md, coding-standards.md, any other) spells its absolute path literally, `<plugin root>/docs/agents/<doc>.md` with `<plugin root>` replaced by the path this session resolved (the rules doc's Plugin root rule), never an environment variable and never a `~/` path: a subagent's Bash has no such variable. A pointer such as "the harness doc's Idle rule" in a brief names that doc by the same absolute path, which the task orchestrator brief below carries as its `<plugin root>`.

`<owner>` outside `~/src`, when it is not the session's repo, makes `bd` and `git` writes fail with `Operation not permitted`: the tracker doc's "bd writes outside the session's repo" says what to do. The session mode, `<home>` and `<workspace>` are as **the one test** in the tracker doc's opening defines them: `<home>` is the session's repo, the workspace for a spawned story orchestrator and the owner repo for a typed one, and plain `bd` reaches its database. Typed in an owner repo, the session is a repo session with no workspace, and what needs another database degrades: the sibling line, the sibling refresh with step 8's sibling re-read (step 3), and the `waiting:` line (step 9) are skipped, and a text blocker in another repo cannot be read, so it counts as open (the Frontier section's unreadable-blocker rule). A story cut in such a repo session runs right there. Only a story whose text blocker is in another repo is run from the workspace session: its wait message says to run `/dev:implement-spec <KEY>-<n>` (or `/dev:implement-spec <epic-id>` when the epic has no external ref) from the workspace root (`/dev:implement-story <story-id>` typed there would take `<owner>` for the workspace and not find the story).

`<KEY>-<n>` is the story's `external_ref`. A story without one has no key: its commits carry `Bead:` alone (no `Refs:`), and the sibling line (`<repo> <story-id> <url>`) and the Jira context below are skipped; its branch is `feat/<story-id>`, as every story's is (step 3).

`<task-slug>` is the task id; `<epic-id>` is the epic bead id on the story's `## Parent` line. **Worktrees**: harness isolation (`isolation: "worktree"`) makes worktrees only in the session's repo, so a subagent working in `<owner>` takes it only when `<owner>` is the session's repo. Otherwise its worktree is hand-rolled inside `<owner>`, as the harness doc's fallback: `git -C <owner> worktree add <owner>/.worktrees/<task-slug> -b task/<task-slug> <integration branch>` (reused if it exists; when only the branch survives, re-add it as the harness doc's fallback says), and the brief gives its absolute path.

## Steps

1. **Read the story and its tasks.** `bd -C <owner> show <story-id> --json` (an array; `.[0]`). Refuse with one line and create nothing when:
   - the bead is an epic with a non-story child: the malformed-epic refusal of the tracker doc's "gather the epic bead" (nothing is suggested);
   - otherwise the bead is not of `issue_type` `story`: `<id> is of type <type>, not a story; /dev:implement-story takes a story bead id.`

   The tasks are `bd -C <owner> children <story-id> --json`. The story's **tier** is the max `complexity:` label among them. The story's notes (`.[0].notes`) are what earlier runs left behind, one line each: `branch:` (step 3), `review:` and `story review <round>` (step 7) and `pr:`, `delivered:` and `checks red:` (step 8); read them once here, the last line of a kind winning. A story is **finished** when every child is `closed` or carries `ready-for-human`, `needs-triage` or `wontfix` (the rules doc's Frontier, Deferrals) and its notes carry a `pr:` line with no `checks red:` line after it (the rules doc's Delivery section's forge-check wait): touch nothing, and go straight to the final report (step 9) with the `pr:` and `branch:` lines read from the notes. The one write it may make: a finished story with no `delivered:` line (delivered before step 8 wrote one) gets it now, the Delivery section's note on the branch's current tip, so `/dev:implement-spec` can review it.

   **Merge guard.** The guard covers a delivered story with an open `ready-for-agent` task: one whose notes carry a `pr:` line, a URL or step 8's `<branch> <tip SHA>` form, while a child that is not closed (open, in_progress or blocked) is labelled `ready-for-agent` (a task added after the first delivery, ADR 0011's add mode). It runs the rules doc's Repo plumbing and Cut-off probe, its Merge guard, with its Forge decision made first (its remote pre-check and proof run here). MERGED: refuse with `<story-id> refused: PR <url> already merged; the new task belongs in a new story: run /dev:spec-to-stories <KEY>-<n> in add mode (or /dev:spec-to-stories <epic-id> when the epic has no external ref); then close <task-id> (moved to the new story)` and create nothing; the line names each open `ready-for-agent` task as `<task-id>`, which stays open under the merged story until add mode has carried its work into a new story, so close it there then (`/dev:close-story` cannot). CLOSED unmerged: refuse with `<story-id> refused: PR <url> is closed unmerged` and create nothing. OPEN: the Merge guard's outcome, the re-delivery path of steps 3 and 8. When the forge cannot tell (no forge, or a branch-form `pr:` note), the section decides the branch form locally first, and `<default branch>` is found as step 3 says. Ask the user only when that cannot decide, whether the PR, or for the branch form the branch, has merged into the default branch, and wait for the answer. In a run spawned by `/dev:implement-spec`, which has no user (the rules doc's Delivery authority), end instead with `failed: <story-id> merge state unknown (<pr: value>): say whether it merged, then re-run` and create nothing.

   Read the story's `## Blocked by` lines and check each as the Frontier section says (a blocker naming a story reads like any bead: open until `/dev:close-story` closes it). While any is open, no task can start: report `<story-id> waits on <repo> <bead-id> <title>` for each (a story blocker adds `merge its PR and run /dev:close-story <blocker-id>`; in a repo session, a blocker in another repo cannot be read: show its line as written in place of the title, and add `run /dev:implement-spec <KEY>-<n> from the workspace root`, or `/dev:implement-spec <epic-id>` when the epic has no external ref), and stop before any branch or commit exists.

2. (optional) Use an **exploration subagent** for any exploration the tasks need. Its brief names the story bead and `<owner>`; it reads the story's design field first (`.[0].design` of its own `bd -C <owner> show <story-id> --json`), the story cut's orientation for this repo, and writes its own notes into `<owner>/.spec-notes/<epic-id>/`, the directory this skill alone owns (the rules doc's Scratch space); every later brief points there by that absolute path.

3. **Integration branch.** A `branch:` line in the story's notes means an earlier run made it: `git -C <owner> switch <name>` if the owner checkout moved off it, and keep any draft PR it opened. Otherwise find the default branch (`git -C <owner> symbolic-ref --short refs/remotes/origin/HEAD` minus `origin/`; with no `origin/HEAD`, whichever of `main` and `master` exists), then `git -C <owner> switch -c feat/<story-id> <default branch>` (the branch is named `feat/<story-id>`, keyed or not: the key stays on commits, the PR body and the bead) and `bd -C <owner> note <story-id> "branch: <name>"`. The owner checkout stays on the integration branch until the run ends; you land each reviewed task onto it there (the Landing section below).

   Apply the rules doc's Repo plumbing and Cut-off probe on the integration branch, `<unit-id>` being `<story-id>`: its Gitignore commit; its Check target, whose `<check command>` every task orchestrator brief carries and step 7 gates on, so every task of the run, parallel siblings included, is gated by the same command (a `resume:` line (step 4's Resumed) keeps the one already resolved); and its Forge decision (already decided in step 1 when the merge guard ran).

   With a forge, open a **draft PR** after the first landing (step 5) (a branch with no commits ahead of the default branch cannot open one). The landings are local, and naming `--head` stops `gh` pushing for you, so first run the rules doc's Delivery section's **stray-commit check** (a hit ends the run there, as that section says), then **push** the integration branch, `git -C <owner> push -u origin <branch>`, on the typed command's authority (the rules doc's Delivery authority); a refused push leaves the draft unopened for now, the frontier is worked on (the landings are local), and step 8 pushes again. With the branch pushed, `gh pr create --draft --repo <forge-slug> --head <branch> --base <default branch> --title "<story title>" --body-file -`, or `tea pr create --repo <owner> --head <branch> --base <default branch> --title "WIP: <story title>" --description "<body>"` (Forgejo treats the `WIP:` prefix as draft). Its body names the story, the Jira key, and one **sibling line** `Part of <KEY>-<n>:` listing the sibling stories: every other `story` bead carrying `<KEY>-<n>` in the manifest's repos (the "Stories" gather in the tracker doc, whose `--json` output carries each sibling's notes). Each sibling appears as `<repo> <story-id> <url>`, the url taken from its `pr:` note; with no `pr:` note, from its draft PR looked up by its `branch:` note in `<workspace>/<repo>`. A sibling's forge is decided from its own `git -C <workspace>/<repo> remote get-url origin`, as the rules doc's Repo plumbing and Cut-off probe, its Forge decision does for the owner: `gh pr list --repo <its forge-slug> --head <branch> --json url -q '.[0].url'`, or `tea pr list --repo <workspace>/<repo> --state open --fields head,url --output json` filtered on `head`. Only when neither exists (a sibling with no forge, or no draft yet), `<repo> <story-id> <branch>`. Then run the **sibling refresh**: in each sibling's open PR, regenerate the whole `Part of <KEY>-<n>:` block from the Stories gather's current notes on every run, listing every story of the feature but that sibling, this story's PR included, and never patch single lines. Both edit commands replace the whole body, so read it first and write all of it back on stdin, with the sibling's own CLI and repo: `gh pr view <n> --repo <its forge-slug> --json body -q .body` then `gh pr edit <n> --repo <its forge-slug> --body-file -`, or `tea api --repo <workspace>/<repo> repos/{owner}/{repo}/pulls/<n> | jq -r .body` then `tea pr edit <n> --repo <workspace>/<repo> --description-file -`. A sibling with no forge or no open PR is skipped. With no forge the integration branch *is* the deliverable; a request for a PR is answered with the branch name.

4. **Work the frontier.** A task of the story that is `in_progress` while no task orchestrator of this run holds it was claimed by a cut-off run (the harness doc's Cut-off agents): `bd -C <owner> unclaim <id>` each first. An unclaim bd refuses because another actor holds the claim is never forced: the task is off this run's frontier, with `failed: <id> claimed by <actor>` in step 9's report. Each task so unclaimed is probed as the rules doc's Cut-off probe says: a hit means its next spawn is a gate entry on the branch, worktree path and tip the probe found (the brief below), a miss a claim entry. Then `bd -C <owner> ready --parent <story-id> -n 0 --json`, keeping only the tasks labelled `ready-for-agent` (the rules doc's Frontier: `bd ready` lists a `ready-for-human` or `needs-triage` child all the same) and minus the tasks that failed twice in this run (step 5; a twice-failed task is open and unclaimed, so `bd ready` lists it, and only this run's count keeps it off). Step 1 already cleared the story's text blockers. Spawn one **task orchestrator** per frontier task with `subagent_type: "general-purpose"` (the rules doc's Subagent type) at `model: opus`, the whole current frontier as one parallel batch in one message, then end your turn: each task orchestrator's report line arrives as the Agent tool's completion notification and resumes you (the harness doc's Waiting: an Agent call returns at once, and you never poll). Fill the short brief below: the task orchestrator runs `/dev:task-orchestrator`, which derives the rest from the task bead. Spawn nothing else per task: the task orchestrator owns the task's implementer and its reviewers; the landing is yours (step 5).

   **Resumed.** A `resume:` line from the epic orchestrator means the batch in flight was cut off and its agents stopped: re-read the story's notes as step 1 does (`branch:`, `review:`, `story review <round>`, `pr:`), keep the check command step 3 resolved, confirm the owner checkout is on the integration branch (step 3), and go to step 6, where the unclaim above returns the cut-off tasks to the frontier. An invocation that was cut off is re-typed by the user and takes the same path from step 1.

   When a text blocker is a publish task (titled `publish <crate> <version>`), the brief also carries the published version: the version in that blocker's `close_reason` (written `published <version>`), which wins over the version in any title. No version in the reason → ask the user for it and wait.

5. **Act on every report of the batch**, each as its notification resumes you. Each task orchestrator reports one line:
   - `<id> reviewed: <task branch> <worktree path> <tip SHA>`: land it now, in the turn this report resumes you, as the Landing section below says; a landing closes the task. The first landing opens the draft PR (step 3).
   - `<id> needs split: <cut>`: create the proposed beads as children of the story, each `bd -C <owner> create --parent <story-id> --labels complexity:<tier>,ready-for-agent --deps blocked-by:<new-id>,... "<title>" --body-file -` with the edges and the tier the cut proposes for that bead (else the original's tier); move every bead the original blocked onto the new ones (`bd -C <owner> dep add <dependent> <new-id>`, so a publish task still waits on all of the story's work); close the original with `bd -C <owner> close <id> --reason "split into <ids>"`.
   - `<id> failed: <reason>`, from the task orchestrator or from your own landing: the task is not closed, and its claim outlives it (the rules doc's Frontier, Unclaim), so first `bd -C <owner> unclaim <id>` (a refusal follows step 4's rule). A first failure gives it one fresh task orchestrator in the next batch with the reason added to its brief; after `failed: red after conflict resolution` that one enters at the gate on the resolved branch, its brief carrying the gate entry and the red record's log (the brief below). Any other first failure is probed once the unclaim is done, step 4's Cut-off probe deciding its entry, so a retry gates the commits that attempt left instead of starting over. A second failure takes the task off the frontier for this run: `bd -C <owner> note <id> "failed twice: <reason>; resume: <command>"` with step 9's resume command, so the task stands open and unassigned, `bd -C <owner> ready --parent <story-id>` lists it, and a resumed run finds the pointer; it is a `failed:` line in step 9's report. An API error in place of a report line is a cut-off, not a failure: the task rejoins the frontier at step 6 through step 4's unclaim, its failure count unchanged.

6. **Re-evaluate the frontier** once every report of the batch has arrived and been handled, and spawn the next batch from it (step 4). Repeat until a batch would be empty. Then:
   - every child is `closed` or carries `ready-for-human`, `needs-triage` or `wontfix`, what step 1 counts as finished short of the `pr:` note → steps 7 and 8. A child carrying one of those labels is not waited for (the rules doc's Deferrals);
   - otherwise skip steps 7 and 8 and go to step 9. The run is a **human stop** if a `ready-for-human` task of the story is open and a **stall** otherwise, as the rules doc says; either way the report names each other child left open.

7. **Story gate.** The story gate is the rules doc's Check gate loop on the integration branch tip, the story row of the rules doc's table: it exits when the checks are green on the tip the review called clean. The check command is the one step 3 resolved for the run, the one every task orchestrator brief carried. Each pass runs the checks first, read from the check records (the rules doc's Check record and Check scope). First confirm `git -C <owner> branch --show-current` prints `<branch>` and confirm the owner checkout is clean, `git -C <owner> status --porcelain` prints nothing (untracked files count, since the check runs on the working tree while the record keys on the committed tree); else skip step 8 and go to step 9 with `failed: <story-id> not on <branch>` or `failed: <story-id> owner checkout dirty: <files>`, `<files>` the paths that status call printed, classified as step 6 says. Then read the tip's tree, `git -C <owner> rev-parse <branch>^{tree}`, as `<tree>`: its record is `<owner>/.tmp/checks/<tree>/record`, and a tree with a green record (`exit=0`) is checked: run nothing, whichever orchestrator wrote it (the common case is the record of the reviewed tip a landing fast-forwarded to: the task orchestrator's last check, or your check of a resolved tree); a red record is no check, so the tree is checked again (the rules doc's Check scope). Otherwise run the check command read-only on the owner checkout, which is on `<branch>`, in one foreground Bash call with `timeout: 600000` (the harness doc's Idle rule) that writes the record: the rules doc's Check record call with `<owner>` as its `<worktree path>`, so a green costs you one `exit=0` line and you never read a log whole; a red is read by `tail -n 40 <log>`, `<log>` the record's log. With the checks green, compare the story's `review:` note with the tip, `git -C <owner> rev-parse <branch>`: the same SHA exits the gate. The story keeps the reviewed tip in its notes: its `review:` note names the tip the gate exits on after a clean review, so a rerun reviews only a tip that has moved past it (a task landed since, in add mode or after a split, or a fix-up). No note, or a tip that has moved since, means the review is due: call the Skill tool with `mattpocock-skills:code-review` on the integration branch since the default branch in `<owner>`, with its two sub-agents run at the review model of the story's tier (one tier up, the rules doc's trust rule 1). The skill reviews the working directory's repo, so the invocation names `<owner>` and spells out what its sub-agents receive: the base SHA `<base>`, `git -C <owner> merge-base <default branch> <branch>`, the diff `git -C <owner> diff <base>..<branch>` and the commit list `git -C <owner> log <base>..<branch> --oneline`, for context; the two axes, as the rules doc's Review scope says, where the spec axis is the story's body (`bd -C <owner> show <story-id>`: what it delivers and its `## Test seams`, where its criteria must be exercised), with the Jira epic `<KEY>-<n>` for the feature context, and the standards axis is what entered since the task reviews: the conflict resolutions and the coherence across tasks, plus this gate's fix-up commits since the last story review (each task's own diff was reviewed at its row and is not read for standards again), each handed over as a command: every merge's resolution, `git -C <owner> show --remerge-diff <merge>` for each `<merge>` of `git -C <owner> log --merges --format=%H <base>..<branch>` (it prints only what the merge resolved by hand), and the fix-up commits, `git -C <owner> log --no-merges --grep='^Bead: <story-id>$' <since>..<branch>` with `-p` (a fix-up commits under the story's id, a task's implementer under the task's), `<since>` the tip the last `story review` note names, else `<base>`, read against the standards sources searched in `<owner>` (its `CODING_STANDARDS.md` or `CONTRIBUTING.md`, `GLOSSARY.md` and `docs/adr/` where they exist) plus `<plugin root>/docs/agents/coding-standards.md` spelled as the path this session resolved (the bullet above), which the skill never finds on its own; and the shape of each sub-agent's report, as the rules doc's Review verdict says: every finding tagged **blocking** or **minor**, the last line `verdict: clean` or `verdict: blocking (<n>)`. Its sub-agents report findings only and create no bead. Write the findings and the verdict on the story, `bd -C <owner> note <story-id> "story review <round> <tip SHA>: <findings>; <verdict line>"`, `<tip SHA>` the tip the review read and `<round>` one more than the last `story review` note's round step 1 read (1 when there is none), so a rerun numbers on rather than restarting. A red or a blocking verdict goes to a fresh implementer by pointer brief and the loop starts over, from the checks; a fix-up that commits moves the tip off any `review:` note, so the next green pass is reviewed again. After a red, a fix-up that commits nothing leaves the tree red-recorded, so the next pass checks it again rather than reading the red; after a blocking verdict its tree keeps its green record, so the pass runs no check and the review runs again; either way that fix-up still spends budget; a green on a tip the `review:` note still names exits (the rules doc's Check gate). **Clean** ends the review, minors or none: the minors go to one last implementer on a fix-up, and the minors fix-up reruns the checks and spends no budget. Once it has landed (or the review found nothing to fix), write the reviewed tip, `bd -C <owner> note <story-id> "review: <tip SHA>"` with the tip re-read (`git -C <owner> rev-parse <branch>`), and the loop starts over, so its next green pass exits; a red there goes to a fresh fix-up like any other, whose new tip the gate reviews. So a first run goes checks, review, minors fix-up, `review:` note, checks, exit; a rerun on a reviewed tip goes checks, exit. A finding the review defers (out of the story's scope, a follow-up, a note with nothing to implement) goes to no implementer and to no child of the story: capture it in the inbox as the tracker doc's "capture a retro item" says (plain `bd` in `<home>`, that section's command, labels and target label, `<KEY>-<n>` as the external ref when there is a key, the finding as the body's Moment), so no later run's frontier sees it (the rules doc's Frontier, Deferrals). Each **fix-up** is a fresh implementer (the rules doc's trust rule 2), at the tier's implementation model in its own worktree (Owner repo's Worktrees rule, slug `fixup-<story-id>`) for the run's first fix-up; every later one in this run, a second or third red or blocking fix-up and the minors fix-up alike, reuses the first's worktree and branch rather than taking a fresh one, on either route, spawned as the harness doc's Worktrees rule spawns an implementer on a fix-up: without `isolation`, into the worktree and branch the first fix-up reported, its brief carrying that path (when the harness has removed that worktree because its implementer changed nothing, the next fix-up takes one as the first did, and the ones after it reuse that one); each has a pointer-only brief: for a red, the failing command and the record's log path, no pasted output; for a review, its `story review <round>` note, of which it fixes the blocking findings and the minors in the story's scope (the note's minors out of the story's scope are findings the review defers, captured as above at once). You relay, you never fix: you land its branch by the same procedure as a task's, the Landing section below (the stray-commit check, then the merge; a conflict to a fresh implementer in that worktree, the resolved tree checked, then a fast-forward), with `<story-id>` in place of the task id and no task to close; no task orchestrator runs during the gate, so `<branch>` cannot move and the fast-forward after a resolution applies, and a red on the resolved tree is a red of this gate, which goes to the next fix-up. The budget is three fix-ups per story, red or blocking alike, as the rules doc's Check gate says; the minors fix-up and a conflict resolution spend none, and the fourth failure skips step 8 and goes to step 9, classified as step 6 says, with a `failed: <check> <command>` line in the report: `failed: check make check` for a red (a review's as `failed: review mattpocock-skills:code-review`). Before any `failed:` line this step sends to step 9, a guard's or the fourth failure's, capture in the inbox every minor of this run's `story review` notes that no fix-up's report names as fixed.

8. **Deliver**, as the rules doc's Delivery section says, with the story as its unit (`<unit-id>` is `<story-id>`, `<branch>` the integration branch, `<check record>` the one step 7's exit read): its stray-commit check before any push, the push, the PR body, the forge-check wait, then the `delivered:` and `pr:` notes in that order. The skill adds only these. Each `failed:` line the Delivery section ends on skips the rest of step 8 and goes to step 9, classified as step 6 says, with no `PR:` line. With a forge, open the draft after the push if step 3 could not, and append the sibling line (rebuilt as in step 3) to the body the Delivery section's PR body step writes, before writing it back. The PR stays a draft (the story row of the rules doc's table): the epic row marks it ready once its epic review is clean (`/dev:implement-spec`'s **Draft until clean**), so an invocation typed in the story's repo leaves it a draft for `/dev:implement-spec <KEY>-<n>` (or `/dev:implement-spec <epic-id>` when the epic has no external ref) or for the human. A red forge check leaves the story not finished even when an earlier delivery left a `pr:` note (step 1): the Delivery section's `checks red:` note is the line step 1 reads. After the `pr:` note, re-read every sibling story's notes (`bd -C <owner> show <sibling-id> --json`), and only then run step 3's sibling refresh. With no forge there is no PR and no sibling refresh to write: the Delivery section's no-forge path applies, and the report names the local branch.

   The story bead stays **open**: `/dev:close-story` closes it after the PR merges. There is no Jira step here.

   If a `ready-for-human` task of the story is still open, the invocation ends in a **human stop** (step 9's report).

9. **Clean up** every worktree that is done with, this run's and earlier runs' alike. First `git -C <owner> worktree prune`, which drops the entries whose directory is already gone. Then sweep `git -C <owner> worktree list --porcelain` for every entry whose branch is `worktree-agent-*` or whose path is under `<owner>/.worktrees/` (a harness worktree, whose `branch` line reads `refs/heads/worktree-agent-<id>`, or a hand-rolled one; the harness doc's Worktrees), so a leftover from a cut-off run goes too; which `<owner>/.worktrees/` entries it may remove, the shape test below decides. The sweep keeps to the owner checkout's own worktrees: an entry is swept only when its `worktree` path lies inside `<top>` (it starts with `<top>/`), `<top>` the path `git -C <owner> rev-parse --show-toplevel` prints, so the `<owner>/.worktrees/` test reads `<top>/.worktrees/`. When `<owner>` is itself a linked worktree, the list sees every worktree of the shared repo, and another checkout's merged `worktree-agent-*` worktree is not this run's to remove (the prune sees them too, and stays repo-wide: it drops only entries whose directory is already gone). Nor is an entry swept when it lies inside another listed worktree (its path starts with that worktree's path and `/`) which itself lies inside `<top>`, so never the `<top>` entry itself: that one is a linked worktree nested in the owner (say `<top>/.worktrees/x`, used as an owner by another run), and the entry (its harness worktree at `<top>/.worktrees/x/.claude/worktrees/agent-<id>`) is that checkout's to sweep. That nested checkout is spared too: a `<top>/.worktrees/` entry that holds another listed worktree (one that lies inside it, as above) is a checkout another run is using as its owner, never a finished hand-rolled task worktree, whose implementer makes no worktree; it is left in place whatever its branch or lock and reported on the `worktrees:` line as `in use: holds <child path>`, since `git worktree remove` refuses only uncommitted changes and deletes ignored contents, its `.claude/worktrees/` children and their unmerged work among them. The children are the signal, not a lock or a marker file that run would take: the harness registers them from that run's first spawn until its own step 9 removes them (it drops one itself only when its subagent changed nothing, so no work goes with it), whichever plugin version or workflow runs there, while a lock or a marker holds only if that run remembers to write it, and one a cut-off run leaves behind blocks every later sweep. A nested owner that holds none, before its run's first spawn or once the harness has dropped every child, is told apart by a second signal that needs nothing from that run either, the entry's shape: under `<top>/.worktrees/` only a hand-rolled task worktree is swept, one whose `branch` line reads exactly `refs/heads/task/<slug>` at `<top>/.worktrees/<slug>`, the same `<slug>` in both (Owner repo's Worktrees rule, a fix-up's `fixup-<story-id>` included), and the shape test holds for every entry under `<top>/.worktrees/`, a `worktree-agent-*` branch there included. Any other `<top>/.worktrees/` entry is not this run's to remove: a nested owner on `feat/<story-id>` among them, which a fresh cut leaves on the default branch tip, so its branch counts as merged and the merge test alone would take its live checkout and ignored scratch (`.spec-notes/`, `.tmp/checks`). It is left in place as a nested owner in use is, reported as `not a task worktree`, a `ticket/<slug>` worktree (the prefix before the rename) included; an entry gets one `worktrees:` line, with the first reason that applies: `in use`, then `not a task worktree`, then the locked, detached and unmerged reasons below. The shape also leaves on the line a `.worktrees/` entry some other hand made, which the path alone sweeps once merged: the human removes it from the report, a cost of one report line, where a wrong removal costs a live run its checkout. Both paths are compared resolved: `--show-toplevel` prints the top level with symlinks followed, and `worktree add` records each worktree's path resolved, which the list prints, so an `<owner>` spelled through a symlink still matches its own entries. A locked one (a `locked` line in its entry) is left alone whatever its branch, and so are a `detached` one (no branch to test) and one whose branch is unmerged: each is reported with its path and the reason on the report's `worktrees:` line, never forced. The rest, whose branch is merged into `<branch>` (`git -C <owner> merge-base --is-ancestor <worktree branch> <branch>` exits 0; any other exit is unmerged), are removed: `git -C <owner> worktree remove <absolute path>` each. One the remove refuses (uncommitted changes in it) stays and goes on the line with git's error. Both `git -C <owner> worktree remove <absolute path>` and `git -C <owner> worktree prune` run with the sandbox disabled, as the forge CLI runs in `/dev:close-story`'s "The forge shows MERGED" section: the sandbox denies deletes under the `worktrees/` directory of the git common directory (`git -C <owner> rev-parse --path-format=absolute --git-common-dir`, which is not under `<owner>` when `.git` is a file) and no setting lifts that, so inside it the remove fails with `Operation not permitted` (or `could not lock config file <path>/config`, the common directory's) and leaves the worktree registered, which is not a git error; a failure outside the sandbox is real and goes on the `worktrees:` line with its error. Each `task/<task-slug>` branch stays; a later run re-adds its worktree as the harness doc's hand-rolled fallback says. Then remove the check records, `rm -rf <owner>/.tmp/checks`, step 8 having copied the delivered tip's into the PR's Evidence (a rerun checks its tree again). A run that ends on step 7's `failed: check <command>` skips the removal and keeps the red check's log in place, whole rather than tailed into the report: it is the branch tip's, `<owner>/.tmp/checks/<tree>/log` with `<tree>` from `git -C <owner> rev-parse <branch>^{tree}` (no fix-up lands after the fourth red), so the human reads why the check failed without rerunning it, and the `failed:` line keeps the rules doc's words. A rerun on that tip checks it again, since a red record is no check (step 7), so a red from outside the tree (a missing tool, a flaky test) does not stick to it. Every other run, a green delivery or one failed for any other reason, removes the records. Leave `<owner>/.spec-notes/` in place. Last, on every path into this step, step 1's finished story included (the read touches nothing), name the untracked files: every path on a `??` line of `git -C <owner> status --porcelain --untracked-files=all` (untracked and not ignored, so nothing under the scratch paths of the rules doc's Gitignore rule shows) goes on a `stray:` line of the report, one per path as git prints it, and none is deleted, moved or committed: a file an agent wrote outside the scratch paths is the human's to judge. With no `??` line there is no `stray:` line.

## Landing

You land each reviewed task branch yourself, in the turn its `reviewed:` report resumes you, as the rules doc's Landing a task says: a `git merge` that applies is a command, not an edit. Landings are **serial**: one runs at a time, one per report, and a `reviewed:` report that arrives while a landing waits on its conflict implementer is held until that landing ends, then landed in arrival order. So there is no lock to wait on: a task orchestrator never touches the owner checkout (`/dev:task-orchestrator`), and `<branch>` moves only under your own landing. `<task branch>`, `<worktree path>` and `<tip SHA>` are the report's; `<task-id>` is its task. A story gate fix-up (step 7) reports its branch and worktree path but no tip SHA: its `<tip SHA>` is `git -C <worktree path> rev-parse HEAD`, read in the turn its report resumes you.

1. Confirm `git -C <owner> branch --show-current` is `<branch>` and the owner checkout is clean (the harness doc's Commits rule: `git -C <owner> status --porcelain --untracked-files=no` prints nothing), else end the landing unmerged with `<task-id> failed: not on <branch>` or `<task-id> failed: owner checkout dirty`; and confirm `git -C <owner> rev-parse <task branch>` prints `<tip SHA>`, the tip the task's review called clean, else `<task-id> failed: <task branch> moved past its reviewed tip`.
2. Run the **stray-commit check** on what the merge brings in (`git -C <owner> log --no-merges --format='%H%x09%ae%x09%(trailers:key=Bead,valueonly,separator=%x2C)%x09%s' <branch>..<task branch>`: a commit whose author is not `git -C <owner> config user.email`, or with no `Bead:` trailer, ends the landing unmerged with `<task-id> failed: stray commit <sha> <subject>`), and merge, `git -C <owner> merge <task branch>`. A merge that applies lands the task: go to 4. When `<branch>` moved since the task's checks, its new tree is the story row's to check (step 7).
3. A conflict goes to an implementer in the task's worktree. First `git -C <owner> merge --abort`, so the owner checkout is clean, then spawn an implementer at the task's tier's implementation model in `<worktree path>` and on `<task branch>` (no `isolation`, `git -C <worktree path>` on either route), its brief starting with the TMPDIR line for that worktree, then the plain-command line, one plain `git` or `bd` command per Bash call, every path spelled out, citing `<plugin root>/docs/agents/harness.md` in one line and naming its Commits rule; it is briefed to merge `<branch>`'s tip into the task branch, resolve the conflict and commit, with `timeout: 600000` on every check and test run and the trailers `Bead: <task-id>` and `Refs: <KEY>-<n>` (no `Refs:` with no key), and to report when done. End your turn; its report resumes you. Then check the **resolved tree**: confirm `git -C <worktree path> status --porcelain` prints nothing (a dirty worktree counts as red and writes no record, so its retry gets no `red log:`), read `<tree>` as `git -C <worktree path> rev-parse HEAD^{tree}`, run nothing on a green record (`exit=0`), else run the rules doc's Check record call with the task's worktree as its `<worktree path>`, `timeout: 600000`. No reviewer runs: the story row's standards axis sees the resolution. Green: repeat 1's branch and clean-tree guards, but not its tip guard, since the resolution moved `<task branch>` past `<tip SHA>`: confirm `git -C <owner> rev-parse <task branch>` prints the resolved tip, `git -C <worktree path> rev-parse HEAD`, the commit whose tree was just checked, else `<task-id> failed: <task branch> moved past its resolved tip`; then 2's stray-commit check, then `git -C <owner> merge --ff-only <task branch>`; a refused fast-forward merges as in 2. Red: end the landing unmerged with `<task-id> failed: red after conflict resolution`; step 5's `failed:` rule unclaims the task, and its one retry is a fresh task orchestrator entering at the gate on the resolved branch, which owns the fix-up and its budget, so you never gate a task yourself. A landing takes at most **three conflict resolutions** (the rules doc's Landing a task), apart from the task's fix-up budget, counted from its first merge until a merge applies, a refused fast-forward's conflict among them; the fourth conflict, after `git -C <owner> merge --abort`, ends it `<task-id> failed: conflict <task branch> after three resolutions`.
4. A landing closes the task: `bd -C <owner> close <task-id>`. The first landing opens the draft PR (step 3).
