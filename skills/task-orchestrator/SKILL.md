**Spawned only.** This skill runs inside a subagent that a story orchestrator spawned with a brief naming a task id, an owner path, an integration branch and a check command. Typed bare, or called without that brief, refuse with exactly one line and do nothing else: `/dev:task-orchestrator is spawned only, by /dev:implement-story or /dev:implement-task; run one of those instead.`

## The brief

The brief carries only what the story run alone knows: `<task-id>`, `<owner>` (the owner repo's absolute path), the integration branch `<branch>`, the check command `<check command>`, the published version `<version>` if any, `<plugin root>` as a literal absolute path, and on a retry the first failure's reason. A **gate entry** adds the task's branch, its worktree path and its tip SHA (`gate entry: <task branch> <worktree path> <tip SHA>`), and the red record's log (`red log: <log>`) when the retry follows a red on a resolved tree. Everything else you derive from the task bead, `bd -C <owner> show <task-id> --json` (an array; `.[0]`): its tier from its `complexity:` label; its story `<story-id>` from its parent (none for a standalone task); the Jira key `<KEY>-<n>` from the story's `external_ref` (a standalone task's own), or none; and `<home>` and the session mode by the one test in the tracker doc's opening, `<plugin root>/docs/agents/issue-tracker.md`.

## Your row

You are the **task orchestrator** for `<task-id>` in `<owner>` (story `<story-id>` or none, Jira `<KEY>-<n>` or none, integration branch `<branch>`, check command `<check command>`, published version `<version>` if any; home `<home>`, a workspace session or a repo session); your row is the task row of the rules doc's table: you build with one implementer in a worktree, check with the check command, review the task's body as the spec axis and the task diff as the standards axis, one tier up, none at `low`, fix up by pointer brief in the same worktree, report the reviewed branch for the story orchestrator to land, and exit when the checks are green on the tip the review called clean, within three fix-ups. The check command is the one in your brief, `make check` (the rules doc's Check command), resolved once for the whole run by the story orchestrator: use it as given and never resolve it yourself. Read the rules doc, `<plugin root>/docs/agents/orchestration.md` (you are an orchestrator for this one task: you never edit files, and every change comes from a subagent you spawn) and the tracker doc, `<plugin root>/docs/agents/issue-tracker.md`, at "start work on a task". The harness mechanics are in `<plugin root>/docs/agents/harness.md` (Waiting, the Idle rule, Commits, Cut-off agents, Worktrees, Literal paths, the TMPDIR line): read it, and every brief you send cites it in one line, by that absolute path, in place of restating its rules. Every agent runs `bd` as `bd -C <owner>`, with one exception: step 3's inbox capture is plain `bd`, which reaches `<home>`'s database from where you run. Absolute file paths, literal paths, one command per Bash call (one exception: step 3's check-record call), no `cd`; every brief you send carries the rules doc's absolute path above (and the tracker doc's when it points there), never a variable or a `~/` path, its one harness-doc line, `<owner>`, the check command, the worktree path when there is one, that agent's `git` rule, the story's test seams as where its tests go, and as its first line the TMPDIR line when the agent works in a worktree (the harness doc's TMPDIR rule: the line, its `export` repeated per Bash call and its `mktemp -d` template), then the plain-command line, one plain `git` or `bd` command per Bash call, every path spelled out; a brief to an agent that commits or merges names the harness doc's Commits rule. The harness doc's Idle rule binds you too: every Bash call in the foreground, `timeout` up to 600000 ms, never a background call or a `Monitor`. Spawn each subagent with an explicit `model:`, then end your turn: its report arrives as the Agent tool's completion notification and resumes you (the harness doc's Waiting: an Agent call returns at once, there is no foreground spawn, and you never poll). First check that you have the Agent tool: without it, report `<task-id> failed: no Agent tool` now and stop (the rules doc's Subagent type).

**The owner checkout is not yours.** You never write to the owner checkout: no `git -C <owner>` merge, commit, switch, reset or checkout, and no file under `<owner>` but your check records under `<owner>/.tmp/checks/` (the rules doc's Check record) and, on the hand-rolled route, step 2's `git -C <owner> worktree add`, which leaves the checkout as it is. You read it only to diff. The story orchestrator lands your branch there and closes the task; you never close it. So parallel task orchestrators never meet in the owner checkout, and whichever story orchestrator spawned you, the procedure is the same.

**`git` rule.** You run `git -C <worktree path>` read-only on the task's worktree. The implementer runs `git -C <worktree path>` on the hand-rolled route, and plain `git` in its own worktree under harness isolation, never `git -C <owner>`; an implementer on a fix-up runs `git -C <worktree path>` on either route.

A subagent that returns an API error, or ends with no report, is replaced by a fresh subagent at the same model in the same worktree (the harness doc's Cut-off agents): an implementer's replacement is briefed as a fix-up's implementer in step 3, with the task as its pointer, since its commits are on the branch, and step 3's round count runs on, no reset within this task orchestrator, which still holds the count. You are a fresh task orchestrator, whether the first for this task, a first failure's retry, a cut-off one's replacement or a resume after `failed twice`, so you start at round 1 with the budget at three, whatever `checks <n>:` or `review <n>:` notes earlier attempts left on the task: your task starts over from `<branch>`'s tip (the rules doc's Check gate), or at a gate entry from the tip your brief names.

## Two entries

One procedure, two entries, selected by the brief and never by you: the **claim entry**, for a fresh task (a brief with no `gate entry:` line), runs steps 1, 2 and 3; the **gate entry**, when the branch already carries commits (a cut-off's replacement, or a retry after a conflict resolution's red), runs step 1, then step 3 on the branch, worktree path and tip the brief names, with a fresh budget and no step 2. Its first pass checks that tip as any pass does: a red record is no check (the rules doc's Check scope), so the resolved tree is checked again, and a red goes to the fix-up with that record's log.

## Steps

1. `bd -C <owner> update <task-id> --claim`. Read its `complexity:` tier.
2. Spawn the **implementer** at the tier's implementation model. Worktree: `isolation: "worktree"` when `<owner>` is your session's repo; otherwise make `git -C <owner> worktree add <owner>/.worktrees/<task-slug> -b task/<task-slug> <branch>` (reuse the worktree if it exists; if only the branch survives an earlier run, re-add it as the harness doc's Worktrees fallback says) and give its absolute path in the brief. The brief starts with the TMPDIR line (on the harness route its first Bash call is `pwd` alone, and the path it printed is spelled literally in every later `export`, never `$PWD`), then the plain-command line, one plain `git` or `bd` command per Bash call, every path spelled out. The implementer resets its worktree onto `<branch>`'s tip first; calls the Skill tool with `mattpocock-skills:tdd` to build the task, its tests at the story's test seams (the story bead's `## Test seams` section; for a standalone task, its own body's `## Test seams`, or where `tdd` agrees them when it has none); passes `timeout: 600000` on every check and test run (the harness doc's Idle rule: at the 120-second default a longer call is moved to the background); commits with `Bead: <task-id>` and `Refs: <KEY>-<n>` trailers (`Bead:` alone with no key); bails out with `bd -C <owner> note` and `needs split` plus a proposed cut when edits spread beyond what the task names or a third red-green cycle hits the same seam; merges `<branch>`'s tip into its branch before reporting; and reports its branch name and worktree path. For `medium` and `high` it reports *ready for review*. Its own check runs never count (the rules doc's trust rule 3): only your check record does. The implementer runs no gate and spawns no one; it is then done, and nothing is sent back to it.
3. **Check gate**, every tier, after the implementer reports and before you report the branch reviewed, as the rules doc's Check gate says: the checks, then the review, one loop. You run the check command yourself, read-only, on the tip of the branch the implementer reported, in its worktree path (it has `<branch>`'s tip merged). First confirm the worktree is clean, `git -C <worktree path> status --porcelain` prints nothing; a dirty worktree goes to a fresh implementer as a red does (its failing command that status call, since the record keys on the committed tree while the check runs on the working tree). A non-ignored file a check leaves in the worktree is a gitignore gap that makes the next guard red, so checks write their outputs under `.tmp/`. Then read the tip's tree, `git -C <worktree path> rev-parse HEAD^{tree}`, as `<tree>`: its check record is `<owner>/.tmp/checks/<tree>/record`, and a tree with a green record (`exit=0`) is checked: run nothing, whichever orchestrator wrote it (the rules doc's Check scope); a red record is no check, so the tree is checked again and the call below replaces the record. Otherwise run the check command in one foreground Bash call with `timeout: 600000` that writes the record, both streams to the record's log and the command and its exit to the record, the call the rules doc's Check record states (`<worktree path>` the task's worktree path), so a green costs you one `exit=0` line and no check output enters your context; you never read a log whole. Only you write a record, never an implementer (the rules doc's Check record). Red: read `tail -n 40 <log>`, `<log>` the record's log, and note `bd -C <owner> note <task-id> "checks <round>: red <command>"` (a green writes no note). A red spawns a fresh implementer on the fix-up and the loop starts over from the checks. The **fix-up's fresh implementer** runs at the tier's implementation model in the same worktree and on the same branch, briefed as the blocking fix-up below with a pointer-only brief: the task id, the worktree path and branch, the failing command, the log path, and no pasted output (the TMPDIR line first, then the plain-command line, one plain `git` or `bd` command per Bash call, every path spelled out, as every worktree brief). The budget is three fix-ups of either cause; the fourth red or blocking verdict is `failed`. After a red, a fix-up that commits nothing leaves the tree red-recorded, so the next pass checks it again rather than reading the red; after a blocking verdict its tree keeps its green record, so the pass runs no check and the review runs again; either way that fix-up still spends budget (the rules doc's Check gate). `<round>` counts both causes, 1 for the first run of the checks and up by one after each fix-up, the number a `review <round>:` note carries too. Green: a `low` task exits the loop, go to step 4; for `medium` and `high`, spawn two **reviewers**, one per axis, as the story row's review runs one sub-agent per axis: both at the tier's review model, one tier up (the rules doc's trust rule 1), as one parallel batch in one message. Brief each to call the Skill tool with `mattpocock-skills:code-review` on the implementer's changes since `<branch>` and to do that skill's sub-agent brief for its own axis itself, spawning no one (a reviewer a task orchestrator spawns has no Agent tool): the **spec reviewer**'s axis is the task's body (`bd -C <owner> show <task-id>`: its acceptance criteria, and the story's test seams, or a standalone task's own body's `## Test seams`, where those criteria must be exercised), and the **standards reviewer**'s is the task diff, read against the skill's smell baseline and the standards sources searched in `<owner>` (its `CODING_STANDARDS.md` or `CONTRIBUTING.md`, `GLOSSARY.md` and `docs/adr/` where they exist) plus `<plugin root>/docs/agents/coding-standards.md` spelled as the path this session resolved, which the skill never finds on its own. Brief both to report findings only, every finding tagged **blocking** or **minor** (blocking: an acceptance criterion unmet, a behaviour wrong, a test missing, or no test at a story seam exercising the criteria, where a standalone task whose body has no `## Test seams` names no seam, so this case does not apply; minor: wording, naming or a nit that changes no behaviour an acceptance criterion names), the report ending on one line, `verdict: clean` when no finding is blocking, else `verdict: blocking (<n>)` with the count. Name the diff and the worktree path in both briefs: on the hand-rolled route `git -C <owner> diff <branch>...task/<task-slug>`, on the harness route `git -C <worktree path> diff <branch>...HEAD`. Combine the two reports into one verdict line of that form, clean only when both are, else blocking with `<n>` the two counts summed, and write both axes' findings and that verdict on the task, `bd -C <owner> note <task-id> "review <round>: <findings>; <verdict line>"`, then act on the verdict as the rules doc's Review verdict says. **Blocking**: a blocking verdict spawns a fresh implementer on the fix-up and the loop starts over from the checks, never straight to the reviewers; that implementer is pointed at that note and fixes the note's blocking findings and its minors in the task's scope, its report naming each minor it fixed and each it left unfixed; the note's minors you judge out of the task's scope go to the inbox at once, as a clean round's do below. It works in the worktree path and on the branch name the implementer reported, with no `isolation` (that would open a new worktree on a new branch) and `git -C <worktree path>` on either route; its brief starts with the TMPDIR line for that worktree, then the plain-command line, one plain `git` or `bd` command per Bash call, every path spelled out; it does not reset the worktree (the commits it fixes are there), and otherwise follows step 2: `tdd`, `timeout: 600000` on every check and test run, the same trailers and bail-out, `<branch>`'s tip merged before it reports. A fresh implementer per fix-up, the same worktree throughout, within the budget above. The minors fix-up spends no budget and advances no round. **Clean** exits the loop, minors or none: no reviewer runs again. The minors go to one last implementer on a fix-up, briefed as above, whose commits move the tip, so the checks run again on its new tree (a red there is a red like any other); those you judge out of the task's scope go instead to the inbox as the tracker doc's "capture a retro item" says (plain `bd`, the one exception above; that section's command, labels and target label for your session mode, `<KEY>-<n>` as the external ref when there is a key, the finding and the task id as the body's Moment) and never to a bead of the story. Every minor still unfixed when you report the task reviewed or failed goes to the inbox the same way: one a fix-up's report names as left unfixed, a minors fix-up's included, and, before you report `failed`, every minor of your `review <round>:` notes that no fix-up's report names as fixed. Either way, go to step 4 once the checks are green on the tip. Never resume an earlier implementer with `SendMessage` (the rules doc's Orchestrator role: its reply would land in the top-level session and your turn would already be over).
4. **Report the reviewed branch.** Read the tip, `git -C <worktree path> rev-parse HEAD`, the tip whose tree step 3's last pass recorded green, and report it with the branch the implementer reported and its worktree path. You land nothing and close nothing: the story orchestrator merges the branch onto `<branch>` and closes the task (the rules doc's Landing a task).

## Report

Report exactly one line, and nothing after it:

- `<task-id> reviewed: <task branch> <worktree path> <tip SHA>`, the checks green on the tip the review called clean;
- `<task-id> needs split: <proposed cut>`, when the implementer bailed out;
- `<task-id> failed: <reason>`, anything you cannot finish (a fourth red or blocking verdict, no Agent tool).
